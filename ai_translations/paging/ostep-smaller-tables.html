الـ Page Tables الصغيرة Paging: Smaller Tables

إزاي بنحل مشكلة إن الـ page tables بتاخد memory كتير جداً — من فكرة الـ pages الأكبر، لحد الـ multi-level tables اللي بتستخدمها معظم الأنظمة الحديثة، وصولاً لـ inverted page tables.

20.0 المشكلة الأساسية

خد أي 32-bit address space، وافترض إن حجم كل page هو 4KB (يعني 2^12 byte)، وكل PTE (page-table entry) حجمها 4 bytes. هيبقى عندك تقريباً مليون virtual page (2^32 / 2^12)، ولما تضربهم في حجم الـ entry هتلاقي الـ page table نفسها بقت 4MB.

المشكلة إن ده لكل process لوحدها — مش table واحدة للنظام كله. لو عندك 100 process شغالة في نفس اللحظة (حاجة عادية جداً)، يبقى إنت محجوز مئات الـ megabytes بس عشان تخزن page tables، من غير ما تكون استخدمت أي حاجة فعلياً.

CRUX إزاي نخلي الـ page tables أصغر، من غير ما نخسر سرعة الوصول للـ translation؟

20.1 الحل الأول: Pages أكبر

لو كبّرنا حجم الـ page نفسها (من 4KB لـ 16KB مثلاً)، عدد الـ entries المطلوبة يقل بنفس النسبة — لأن كل entry دلوقتي بتغطي مساحة أكبر من الـ address space.

المشكلة: الـ pages الكبيرة بتسبب internal fragmentation — الـ application بتاخد page كاملة بس تستخدم جزء صغير منها، والباقي بيتهدر جوه نفس الـ page. عشان كده أغلب الأنظمة (زي x86) بتفضّل pages صغيرة نسبياً (4KB).

20.2 الحل التاني: Hybrid (Paging + Segmentation)

الفكرة أصلها من نظام Multics القديم: بدل page table واحدة للـ address space كله، اعمل page table منفصلة لكل segment (code, heap, stack). الـ base register بقى بيشاور على مكان page table الـ segment نفسها في الـ memory، مش على الـ segment مباشرة، والـ bound register بيحدد عدد الـ entries الصالحة فيها.

خد مثال بسيط: address space حجمها 16KB بـ pages مقاسها 1KB. لو الكود بيستخدم page واحدة بس، والـ heap page واحدة، والـ stack صفحتين — باقي الـ address space فاضي تماماً:

شايف إزاي أغلب الـ page table فاضية (invalid)؟ ده هدر واضح، وده بس لـ address space صغيرة جداً — تخيل الوضع في 32-bit address space حقيقية.

TIP · USE HYBRIDS لما يكون عندك فكرتين كويسين لكن مختلفين، دايماً جرّب تجمعهم مع بعض — زي ما الـ Multics فريق جمعوا paging مع segmentation.

مشاكل الحل ده:

  • لسه معتمد على segmentation، اللي مش مرنة كفاية — لو الـ heap كبيرة بس sparse (متفرقة الاستخدام)، لسه هتهدر مساحة.
  • بيرجّع مشكلة external fragmentation — لأن أحجام الـ page tables بقت مختلفة عن بعضها، فصعب تلاقي مساحة فاضية مناسبة لكل واحدة.

20.3 Multi-Level Page Tables

ده الحل اللي فعلياً بتعتمد عليه أنظمة زي x86 لحد دلوقتي. الفكرة: قسّم الـ page table لقطع بحجم page واحدة، ولو قطعة كاملة كلها invalid، متحجزش لها مساحة أصلاً.

عشان تعرف مين القطع المحجوزة، بتستخدم structure جديدة اسمها page directory. كل entry فيها (اسمها PDE) بتقولك: القطعة دي من الـ page table موجودة فين، أو إنها كلها invalid.

في الـ multi-level، بس القطعتين اللي فيهم valid entries هما اللي بياخدوا مساحة فعلية في الـ memory — الباقي "مش موجود" أصلاً، مش بس مُعلّم كـ invalid.

مميزات وعيوب

  • ميزة: بتحجز مساحة على قد الاستخدام الفعلي بس، مش على قد كل الـ address space.
  • ميزة: كل قطعة بتترتب جوه page واحدة بالظبط، فسهل على الـ OS يحجز لها مكان — عكس الـ linear table اللي المفروض تبقى كلها contiguous في الـ physical memory (وده صعب لجدول كبير زي 4MB).
  • عيب: على كل TLB miss، محتاج load اتنين من الـ memory بدل واحد (واحد للـ page directory، وواحد للـ PTE نفسها) — ده time-space trade-off واضح.
  • عيب: تعقيد أكبر في الـ hardware/OS اللي بيعمل الـ lookup.

مثال تفصيلي

افترض address space مقاسها 16KB بـ pages مقاسها 64-byte — يعني 14-bit virtual address، منها 8 bits للـ VPN و6 bits offset. الـ VPN بننقسم لـ Page Directory Index (أول 4 bits) وPage Table Index (4 bits اللي بعدهم):

PD Indexbits 7-4
PT Indexbits 3-0
Offset6 bits

لو عندنا العنوان 0x3F80 (اللي بيشاور على أول byte من VPN رقم 254): أول 4 bits بتختار آخر entry في الـ page directory، اللي بيقولنا إن القطعة دي موجودة في PFN 101. بعدين الـ 4 bits اللي بعدهم بيختاروا الـ entry جوه القطعة دي، فنلاقي إن الصفحة اتماب على PFN 55. بندمج PFN 55 مع الـ offset، ونطلع بالعنوان الفعلي في الـ physical memory.

لما مستويين مش كفاية

لو الـ address space كبيرة والـ page صغيرة، ممكن حتى الـ page directory نفسها تكبر لدرجة إنها متترتبش جوه page واحدة! الحل: قسّم الـ page directory كمان لقطع، وحط page directory تاني فوقها. كده بقى عندك 3 مستويات بدل 2:

مهم توضيح إن كل الـ walk المعقد ده بيحصل بس لما يبقى فيه TLB miss. لو الـ translation موجودة في الـ TLB أصلاً (hit)، العنوان بيتكوّن على طول من غير ما نلمس الـ page table خالص:

20.4 Inverted Page Tables

توفير أقصى للمساحة: بدل page table منفصلة لكل process، اعمل table واحدة global للنظام كله، فيها entry واحدة لكل physical frame (مش لكل virtual page). كل entry بتقول: الفريم ده مستخدم من أي process، وبيتماب على أي virtual page بتاعتها.

المشكلة: لازم search جوه الـ table دي عشان تلاقي الـ entry الصح، والـ linear scan هتبقى بطيئة. الحل الشائع: بناء hash table فوق الـ structure عشان يسرّع الـ lookup. PowerPC مثال معروف بيستخدم الأسلوب ده.

20.5 Swapping الـ Page Tables على الـ Disk

حتى بعد كل الحيل اللي فاتت، ممكن الـ page tables تفضل كبيرة جداً وميتحطوش كلها في الـ memory مرة واحدة. الحل: بعض الأنظمة بتحط الـ page tables دي في kernel virtual memory، فتقدر تعمل swap لأجزاء منها على الـ disk وقت ما الـ memory تحت ضغط.

20.6 الخلاصة

كل الحلول اللي شفناها بتوضح مبدأ واحد: الـ page table هي مجرد data structure، وأي data structure عندها time-space trade-off. كل ما الـ structure أصغر (وفّرت مساحة)، كل ما الوصول ليها أبطأ — خصوصاً وقت TLB miss.

  • Memory محدودة؟ الـ structures الصغيرة (multi-level, inverted) أنسب.
  • Memory متاحة + workload بتستخدم عدد كبير من الـ pages فعلياً؟ يمكن تفضّل structure أكبر تسرّع التعامل مع الـ TLB misses.

الاختيار الصح دايماً بيعتمد على قيود النظام اللي شغال عليه — مفيش حل واحد يناسب الكل.
