الـ TLB — ليه الـ Paging مش هيبقى بطيء

ملخص وشرح بالعربي المصري لفصل الـ Translation-Lookaside Buffer من OSTEP، مبني على القراية مش ترجمة حرفية.

19.0 المشكلة الأول

لما بتستخدم paging، بتقسم الـ address space بتاع البروسيس لحتت صغيرة ثابتة الحجم اسمها pages. المشكلة إن ده بيولّد كمية كبيرة من الـ mapping information (يعني الـ page table) اللي لازم تتخزن في الـ physical memory.

يعني عمليًا: كل مرة البروسيس عايز يعمل access لأي virtual address — سواء عشان يجيب instruction يشغّلها، أو يعمل load/store — الـ hardware المفروض يروح يقرا الـ page table الأول عشان يترجم العنوان ده. يعني كل access حقيقي واحد للـ memory بيتحول لـ access مضاعف: واحد للـ translation وواحد للداتا نفسها. لو ده بيحصل مع كل instruction، الأداء هيبقى وحش جدًا.

THE CRUX — إزاي نسرّع الـ address translation؟
إزاي نقدر نسرّع عملية الـ translation، ونتفادى الـ extra memory reference اللي الـ paging بيفرضها؟ ونحتاج إيه من الـ hardware ومن الـ OS عشان كده يحصل؟

19.1 الحل: TLB

الحل اللي اتعمل: نضيف hardware cache صغير جوه الـ MMU (memory-management unit) اسمه TLB — translation-lookaside buffer. وظيفته إنه يخزن أشهر الـ virtual-to-physical translations اللي البروسيس بيستخدمها كتير، عشان لو احتجتها تاني تلاقيها جاهزة من غير ما تدخل تدور في الـ page table تاني. الاسم الأدق ليه كان لازم يكون address-translation cache، بس التسمية التاريخية عالقة.

كل ما يجيلك virtual address جديد، الـ hardware بيعمل الآتي:

  • يقسم العنوان لـ جزئين: VPN (virtual page number) وoffset جوه الصفحة.
  • يدوّر على الـ VPN ده جوه الـ TLB.
  • لو لقاه (TLB hit): معناها الترجمة موجودة كاش جاهزة. ياخد الـ PFN (physical frame number) من الـ TLB entry على طول، يركّبه مع الـ offset، ويوصل للـ physical address — من غير ما يلمس الـ page table خالص. طبعًا بعد ما يتأكد إن الـ protection bits بتسمح له بالـ access ده (read/write/execute).
  • لو مالقهوش (TLB miss): يضطر يروح يقرا الـ page table من الـ physical memory، يتأكد إن الـ entry دي valid ومسموح له يوصلها، وبعدين يحدّث الـ TLB بالترجمة الجديدة دي، ويعيد تنفيذ نفس الـ instruction من الأول — والمرة دي هيلاقيها hit.
// شرح مبسّط لمنطق الـ hardware عند كل access
VPN = extract_vpn(virtual_address)
(found, entry) = tlb_lookup(VPN)

if found:                         // TLB hit
    if not allowed(entry.protection_bits):
        raise PROTECTION_FAULT
    physical_address = (entry.PFN << shift) | offset
    access_memory(physical_address)     // سريع، بلا لمس للـ page table

else:                              // TLB miss
    pte = read_page_table_entry(VPN)    // extra memory reference
    if not pte.valid:
        raise SEGMENTATION_FAULT
    if not allowed(pte.protection_bits):
        raise PROTECTION_FAULT
    tlb_insert(VPN, pte.PFN, pte.protection_bits)
    retry_instruction()                 // المرة الجاية هتبقى hit

لاحظ إن الـ TLB miss مكلف مش بس عشان في memory reference إضافي، لكن كمان عشان بعده لازم تعيد تنفيذ الـ instruction من الأول. عشان كده الهدف الأساسي دايمًا إننا نقلل عدد الـ misses قد ما نقدر — لأن الـ TLB زي أي cache تاني، بيبقى مفيد بس لو الـ hit rate عالي.

19.2 مثال: الوصول لـ array

علشان نفهم إزاي الـ TLB بيأثر عمليًا، تخيل عندك array فيه 10 عناصر، كل عنصر 4 bytes (integer)، وبيبدأ من virtual address 100. وعندك نظام صغير تخيلي: address space من 8 bits، وحجم الـ page 16 byte — يعني كل عنوان بيتقسم لـ 4 bits VPN و4 bits offset.

لو رسمنا إزاي الـ array ده اتوزع على الصفحات:

VPN = 06 (offset 04-15)
a[0] a[1] a[2]
VPN = 07
a[3] a[4] a[5] a[6]
VPN = 08
a[7] a[8] a[9]

دلوقتي تخيل loop بسيط بيمر على كل عناصر الـ array ويجمعها. كل access للـ array بيتحول لسؤال: "الـ VPN بتاعه موجود في TLB ولا لأ؟" النتيجة بتبقى كده:

العنصرa[0]a[1]a[2]a[3]a[4]a[5]a[6]a[7]a[8]a[9]
النتيجة misshithit misshithithit misshithit

يعني: miss, hit, hit, miss, hit, hit, hit, miss, hit, hit — أول access لكل صفحة جديدة بيبقى miss (لازم يجيب الترجمة أول مرة)، وبعد كده كل العناصر الباقية اللي في نفس الصفحة بتبقى hit. الـ hit rate هنا = 7 من 10 = 70%.

المفاجأة إن ده حصل رغم إن الـ array دي أول مرة تتقرا خالص — والسبب هو مبدأ اسمه spatial locality: العناصر متجاورة في الذاكرة، فأول ما تجيب ترجمة صفحة واحدة، باقي العناصر اللي فيها بتستفاد مجانًا. ولو حجم الـ page كان أكبر (32 byte بدل 16 مثلاً)، كنا هنلاقي misses أقل، وده اللي بيحصل فعليًا في الأنظمة الحقيقية (pages بحجم 4KB) — الوصول للـ arrays بيبقى فيه miss واحد بس لكل صفحة.

ولو نفس الـ loop اتكرر تاني بعد كده على نفس الـ array، هتلاقي كل الـ accesses hits — وده بسبب temporal locality: العناصر اتعملها access قريب، فالترجمة لسه في الـ TLB.

TIP — Caching في العموم
فكرة الـ caching كلها مبنية على نوعين من الـ locality: temporal locality (اللي استخدمته دلوقتي، غالبًا هتستخدمه تاني قريب — زي متغيرات الـ loop) وspatial locality (لو وصلت لعنوان x، غالبًا هتوصل لحاجة قريبة منه). أي hardware cache — سواء TLB أو data cache — بيستغل المبدأين دول. وليه مش بنعمل الـ cache كبير جدًا عشان يخزن كل حاجة؟ لأن أي cache كبير بيبقى أبطأ بطبيعته (قيود فيزيائية زي سرعة الإشارة جوه الشريحة)، فاحنا مضطرين نفضل عندنا cache صغير وسريع.

19.3 مين بيتعامل مع الـ TLB miss؟

فيه مدرستين مختلفتين تمامًا في التعامل مع الـ TLB miss:

1) Hardware-managed TLB

الـ hardware نفسه هو اللي بيتعامل مع الـ miss بالكامل — من غير ما الـ OS يتدخل. الـ hardware لازم يكون عارف بالظبط فين الـ page table في الذاكرة (عن طريق register زي page-table base register)، وشكلها بالظبط. لو miss حصل، الـ hardware نفسه بيعمل page-table walk، يجيب الـ translation، يحدّث الـ TLB، ويعيد المحاولة. النمط ده اتربط تاريخيًا بمعماريات CISC — زي Intel x86 القديمة، اللي بتستخدم CR3 register للإشارة للـ page table الحالي.

2) Software-managed TLB

المعماريات الأحدث (زي RISC — MIPS, SPARC) بتاخد نهج مختلف: لو miss حصل، الـ hardware بس بيرفع exception ويوقف تنفيذ التعليمات، يرفع الـ privilege level لـ kernel mode، ويقفز لـ trap handler — وده كود مكتوب جوه الـ OS نفسه مخصوص لمعالجة الـ TLB misses. الكود ده بيدور على الترجمة في الـ page table، يحدّث الـ TLB بأوامر خاصة (privileged instructions)، وبعدين يرجع من الـ trap.

فيه تفصيلة مهمة جدًا هنا: الرجوع من الـ trap بتاع TLB miss لازم يرجع الـ execution لنفس الـ instruction اللي سببت الـ miss (مش اللي بعدها زي حالة الـ system call العادية) — عشان تتنفذ تاني ودلوقتي تبقى hit.

وتفصيلة تانية مهمة: الـ OS لازم ياخد باله إن كود معالجة الـ TLB miss نفسه ممكن يسبب سلسلة لا نهائية من الـ misses (miss جوه miss). الحل: إما إن الكود ده يتحط في physical memory مش محتاج ترجمة أصلاً، أو إن جزء من الـ TLB نفسه يتحجز entries دايمًا valid (اسمها wired entries) مخصصة لكود المعالجة ده.

ميزة الـ software-managed هي المرونة — الـ OS حر يستخدم أي بنية بيانات يحبها للـ page table من غير ما يحتاج تغيير في الـ hardware — بالإضافة إن الـ hardware بيبقى أبسط بكتير (بس يرفع exception ويسيب الباقي للـ OS).

ASIDE — TLB valid bit مش نفس الـ Page Table valid bit
غلطة شائعة إن الناس تلخبط بينهم. الـ valid bit في الـ page table معناها إن الصفحة دي أصلاً مش متخصصة (allocated) للبروسيس، فلو حاول يوصلها ده خطأ برنامج (يؤدي لـ segmentation fault و kill للبروسيس). أما الـ valid bit في الـ TLB فمعناها بس: هل الـ slot ده جوه الـ TLB فيه ترجمة كاش حاليًا ولا فاضي؟ لما النظام يبدأ تشغيل، كل TLB entries بتكون invalid لأنه لسه محدش خزّن حاجة. وده مفيد جدًا وقت الـ context switch كمان — تخليهم كلهم invalid عشان البروسيس الجديد ميستخدمش بالغلط ترجمات بروسيس تاني.

19.4 إيه اللي جوه الـ TLB entry؟

عادة الـ TLB بيكون فيه 32 أو 64 أو 128 entry، وبيكون fully associative — يعني أي ترجمة ممكن تتحط في أي مكان جوه الـ TLB، والـ hardware بيدور في كل الـ entries بالتوازي (parallel) عشان يلاقيها بسرعة. شكل الـ entry تقريبًا:

VPNPFNother bits
......valid / protection / ASID / dirty ...

الـ "other bits" دي مهمة: فيه valid bit (شرحناه فوق)، وفيه protection bits بتحدد نوع الـ access المسموح — مثلاً صفحات الكود (code pages) بتتحدد كـ read+execute، وصفحات الـ heap بتتحدد كـ read+write. وفيه bits تانية زي address-space identifier وdirty bit هنشرحهم دلوقتي.

19.5 المشكلة الكبيرة: Context Switches

لما بتحصل context switch بين بروسيسين، الترجمات اللي في الـ TLB بتخص بس البروسيس اللي كان شغال. لو انتقلنا لبروسيس تاني من غير احتياط، ممكن يستخدم بالغلط ترجمة بتخص بروسيس مختلف تمامًا.

مثال: لو P1 شغال، والصفحة الافتراضية رقم 10 بتاعته بتترجم لـ physical frame 100. ولو P2 (بروسيس تاني) الصفحة رقم 10 بتاعته هي كمان بتترجم لـ physical frame تاني (170). لو الاتنين موجودين في نفس الـ TLB مع بعض من غير أي تمييز، الـ hardware مش هيعرف يفرّق: VPN=10 بتترجم لـ 100 ولا 170؟

THE CRUX — إزاي ندير محتوى الـ TLB وقت الـ context switch؟
الترجمات القديمة بتاعة البروسيس اللي شغال قبل كده مالهاش معنى للبروسيس الجديد. الـ hardware أو الـ OS لازم يحلوا المشكلة دي.

الحل الأول: Flush كامل

أبسط حل: امسح الـ TLB بالكامل عند كل context switch (خلي كل الـ valid bits = 0). ده بيحل المشكلة بشكل مضمون، بس بثمن: كل بروسيس جديد لما يبدأ يشتغل هيضطر يمر بسلسلة TLB misses من الأول عشان يعمّر الـ TLB تاني — ولو الـ context switching بيحصل كتير، التكلفة دي بتبقى كبيرة.

الحل الأتقن: ASID

بعض الأنظمة بتضيف field جوه كل TLB entry اسمها ASID (address-space identifier) — زي رقم identifier للبروسيس بس بعدد bits أقل (مثلاً 8 bits بدل 32 bit PID). بالطريقة دي، الـ entries بتاعة بروسيسات مختلفة تقدر تتعايش مع بعض جوه نفس الـ TLB من غير أي تلخبط — لأن الـ hardware بيقارن الـ ASID كمان مش بس الـ VPN. الـ OS بيحدد الـ ASID الحالي عن طريق register مخصص وقت الـ context switch، وبكده مفيش حاجة اسمها flush ضروري في كل مرة.

حالة إضافية: Shared pages

ممكن كمان يحصل إن بروسيسين مختلفين يشتركوا في نفس الـ physical page (زي code page لمكتبة مشتركة shared library). في الحالة دي هتلاقي entries مختلفة (VPN مختلف لكل بروسيس، ASID مختلف) لكن كلهم بيشيروا لنفس الـ PFN. ده مفيد جدًا لأنه بيقلل عدد الـ physical pages المستخدمة فعليًا، وبالتالي بيقلل استهلاك الذاكرة.

19.6 Replacement Policy

زي أي cache، لما الـ TLB يبقى فاضي مكان جديد عشان يضيف entry جديدة، لازم يشيل واحدة قديمة — السؤال: يشيل مين؟

  • LRU (Least-Recently-Used): يشيل الـ entry اللي مالهاش استخدام من أطول فترة، بناءً على افتراض إن الحاجة اللي ماتستخدمتش من زمان مش هتتستخدم قريب. ده بيستغل الـ locality الطبيعية في البرامج. لكن فيه حالة سيئة جدًا ليه: لو برنامج بيعمل loop على n+1 صفحة والـ TLB حجمه n بس، الـ LRU هيعمل miss في كل access واحد واحد بدون استثناء!
  • Random: يشيل entry عشوائي. بسيط، وبيتفادى بالظبط الحالة السيئة اللي فوق دي — في نفس السيناريو (loop على n+1 صفحة) الـ random بيدي أداء أحسن بكتير من الـ LRU.

19.7 مثال حقيقي: MIPS R4000

الـ MIPS R4000 بيدعم address space حجمه 32-bit وpages حجمها 4KB — يعني المفروض نستنى VPN حجمه 20 bit وoffset حجمه 12 bit. لكن الـ TLB entry الحقيقي بيستخدم بس 19 bit للـ VPN — لأن عناوين الـ user process بتيجي بس من نص الـ address space (النص التاني محجوز للـ kernel).

الـ VPN بيترجم لـ PFN حجمه لحد 24-bit، يعني النظام يقدر يدعم لحد 64GB physical memory. باقي الحقول المهمة:

  • Global bit (G): للصفحات المشتركة بين كل البروسيسات — لو الـ bit ده متفعّل، الـ ASID بيتجاهَل تمامًا.
  • ASID (8-bit): زي ما شرحنا فوق.
  • Coherence bits (C): بتحدد إزاي الصفحة دي بتتعامل معاها الـ hardware caching.
  • Dirty bit: بيتحدد لما الصفحة تتكتب فيها.
  • Valid bit: هل فيه ترجمة حقيقية في الـ entry دي.
  • Page mask field: بيدعم أحجام صفحات مختلفة (هنشوف ليه ده مفيد في الفصل الجاي).

عادة الـ TLB بتاع MIPS بيكون فيه 32 أو 64 entry، وبعضها محجوز للـ OS نفسه (عن طريق register اسمه wired بيحدد كام entry محجوزة). الـ OS بيستخدم الـ entries المحجوزة دي لكود ومعلومات حساسة زمنيًا — زي كود معالجة الـ TLB miss نفسه — عشان يضمن إنه مش هيحصله miss وهو بيعالج miss تاني.

وعشان الـ TLB ده software-managed، الـ MIPS بيوفر 4 instructions مخصصة لإدارته: TLBP (يفحص هل ترجمة معينة موجودة)، TLBR (يقرا محتوى entry)، TLBWI (يستبدل entry محددة)، TLBWR (يستبدل entry عشوائية). كل التعليمات دي لازم تكون privileged — لأن لو أي user process قدر يعدّل الـ TLB بنفسه، يقدر يعمل أي حاجة يعني أي حاجة (يستولي على الجهاز بالكامل مثلاً).

TIP — RAM مش دايمًا RAM (Culler's Law)
اسم الـ RAM (random-access memory) بيوحي إن كل الأماكن في الذاكرة سريعة الوصول بنفس القدر. لكن بسبب أشياء زي الـ TLB، الوصول لصفحة مش موجودة حاليًا في الـ TLB ممكن يبقى أبطأ بكتير من صفحة موجودة كاش. يعني لو برنامجك بيوصل لعدد صفحات أكبر من سعة الـ TLB، هتلاقي تدهور ملحوظ في الأداء حتى لو الوصول "عشوائي" في الظاهر.

19.8 الخلاصة

الـ TLB بيخلي البرنامج يشتغل تقريبًا كأن الذاكرة مش بتتعمل لها virtualization خالص — وده إنجاز كبير، وأساسي عشان الـ paging يبقى عملي في الأنظمة الحديثة أصلاً.

لكن مش كل حاجة وردي: لو البرنامج بيوصل لعدد صفحات مختلفة في فترة قصيرة أكبر من سعة الـ TLB (يعني بيتخطى الـ TLB coverage)، هيحصله عدد كبير من الـ misses والأداء هيقل بشكل واضح. المشكلة دي بتظهر بكثرة في برامج زي أنظمة قواعد البيانات (DBMS) اللي بتوصل بشكل عشوائي لبنى بيانات كبيرة جدًا.

الحل اللي هيتكلم عنه الفصل الجاي: دعم larger page sizes — كل صفحة أكبر تغطي مساحة أكبر بنفس عدد الـ TLB entries، فتزيد الـ effective coverage.

نقطة أخيرة: الـ TLB ممكن يبقى عنق زجاجة (bottleneck) في الـ CPU pipeline، خصوصًا مع الـ physically-indexed caches اللي محتاجة تعمل الـ translation الأول قبل ما توصل للـ cache. عشان كده فيه تصميمات بتحاول توصل للـ cache باستخدام الـ virtual address مباشرة (virtually-indexed caches) لتفادي التأخير ده — لكن ده بيجيب معاه مشاكل تصميم هاردوير تانية.

تمرين عملي (لو حابب تجرب): تقدر عمليًا تقيس حجم الـ TLB بتاعك بنفسك — تعمل loop بيوصل لعدد pages بيزيد تدريجيًا جوه array كبيرة، وتقيس الزمن لكل access. طول ما عدد الصفحات أقل من سعة الـ TLB، الوقت هيفضل شبه ثابت وسريع. أول ما تتخطى السعة دي، هتلاقي قفزة واضحة في الزمن — وده بيوريك عمليًا فين حدود الـ TLB (وأحيانًا بيبان فيه أكتر من مستوى TLB، يعني L1 وL2).
