متغيرات الشرط (Condition Variables)

Condition Variables

الأقفال (locks) لوحدها مش كفاية. أحيانًا الـthread محتاج "ينام" لحد ما شرط معيّن يبقى صح — زي parent بينتظر child يخلص. الفصل ده بيقدّم condition variable: أداة تخلي الـthread ينام من غير ما يحرق الـCPU وهو بيلف فاضي، وتوريك كمان أد إيه سهل تكتب bug خطير وانت بتستخدمها لو مش حاسب.

01 · البداية

المقدمة والتحدي

لحد دلوقتي عرفنا الـlock وشفنا إزاي بيتبني صح بمساعدة الـhardware والـOS. لكن الأقفال مش الأداة الوحيدة اللي محتاجينها عشان نكتب برامج متزامنة. في حالات كتير، الـthread عايز يتأكد إن شرط معيّن بقى صح قبل ما يكمل — مثلاً parent thread عايز يتأكد إن الـchild thread خلص قبل ما يكمل هو (ده غالبًا بيتسمى join()). السؤال: إزاي ننفذ الانتظار ده؟

شكل 30.1 — Parent بينتظر الـchild — بس إزاي؟ (الكود ده لسه ناقص)
void *child(void *arg) {
    printf("child\n");
    // XXX إزاي نقول إننا خلصنا؟
    return NULL;
}

int main(int argc, char *argv[]) {
    printf("parent: begin\n");
    pthread_t c;
    Pthread_create(&c, NULL, child, NULL); // child
    // XXX إزاي ننتظر الـchild؟
    printf("parent: end\n");
    return 0;
}

الناتج اللي عايزينه واضح: parent: begin ثم child ثم parent: end — بالترتيب ده بالظبط، مهما كان الـscheduling.

محاولة أولى: Busy-waiting بمتغيّر مشترك

أبسط حل ممكن يخطر على بالك: متغيّر done مشترك، الـparent يفضل يعمل عليه while (done == 0) ; (لف فاضي) لحد ما الـchild يخلص ويغيّر قيمته.

شكل 30.2 — Parent بينتظر الـchild — حل بالـSpin
volatile int done = 0;

void *child(void *arg) {
    printf("child\n");
    done = 1;
    return NULL;
}

int main(int argc, char *argv[]) {
    printf("parent: begin\n");
    pthread_t c;
    Pthread_create(&c, NULL, child, NULL); // child
    while (done == 0)
        ; // spin (لف فاضي)
    printf("parent: end\n");
    return 0;
}

الحل ده هيشتغل فعلاً، لكنه مضيعة رهيبة — الـparent بيقعد يلف ويستهلك CPU كامل وهو مش بيعمل أي حاجة مفيدة أصلاً، لحد ما الـchild يخلص. لو الانتظار طال، ده هدر حقيقي لموارد المعالج ممكن يبطّئ threads تانية شغالة على نفس الجهاز.

CRUX: إزاي ننتظر شرط معيّن؟

في البرامج متعددة الـthreads، غالبًا محتاجين thread ينتظر شرط معيّن يبقى صح قبل ما يكمّل. الطريقة البسيطة — إنك تلف (spin) لحد ما الشرط يتحقق — غير فعّالة خالص وبتحرق دورات المعالج، وفي حالات معيّنة ممكن كمان تبقى غلط تمامًا. فإزاي الـthread المفروض ينتظر شرط بطريقة صحيحة وفعّالة؟

اللي إحنا محتاجينه بدل ده: طريقة تخلي الـparent ينام فعليًا لحد ما الشرط اللي بينتظره (إن الـchild خلص مثلاً) يبقى صح — من غير ما يستهلك أي CPU وهو نايم.

02 · الأداة الجديدة

تعريف الـCondition Variable والعمليات بتاعتها

عشان thread ينام لحد ما شرط يبقى صح، بيستخدم حاجة اسمها condition variable. ببساطة، هي طابور انتظار صريح (explicit queue) — أي thread لاقي إن حالة معيّنة (شرط) مش زي ما هو عايز، يقدر "يحط نفسه" في الطابور ده (بالانتظار على الشرط). وأي thread تاني، لما يغيّر الحالة دي، يقدر يصحّي واحد (أو أكتر) من الـthreads النايمة دي (بالإشارة على الشرط). الفكرة أصلها من "الـprivate semaphores" بتاعة Dijkstra، وHoare سمّاها لاحقًا condition variable في شغله على monitors.

عشان تعلن condition variable بتكتب حاجة زي pthread_cond_t c; (ومحتاج طبعًا init صحيح كمان). فيه عمليتين أساسيتين مرتبطين بيها:

  • wait() — بينفذها الـthread لما عايز ينوّم نفسه.
  • signal() — بينفذها thread غيّر حاجة في البرنامج وعايز يصحّي thread نايم على الشرط ده.
شكل posix_sig — توقيع الدالتين في POSIX (هنشير لهم بـwait() وsignal() للاختصار)
int pthread_cond_wait(pthread_cond_t *c, pthread_mutex_t *m);
int pthread_cond_signal(pthread_cond_t *c);

حاجة مهمة تلاحظها: wait() بتاخد mutex كمان كباراميتر — وبتفترض إن اللوك ده متاخد (locked) وقت ما تتنده. مسؤولية wait() إنها تسيب اللوك وتنوّم الـthread في عملية واحدة ذرّية (atomically)؛ ولما الـthread يصحى (بعد ما thread تاني يعمله signal)، لازم يرجع ياخد اللوك تاني قبل ما يرجع للكود اللي نادى عليه. التعقيد ده كله سببه إننا عايزين نمنع race conditions معيّنة من إنها تحصل وقت ما thread بيحاول ينوّم نفسه.

الحل الصح لمشكلة الـjoin

شكل 30.3 — Parent بينتظر الـchild — باستخدام condition variable
int done = 0;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t c = PTHREAD_COND_INITIALIZER;

void thr_exit() {
    Pthread_mutex_lock(&m);
    done = 1;
    Pthread_cond_signal(&c);
    Pthread_mutex_unlock(&m);
}

void *child(void *arg) {
    printf("child\n");
    thr_exit();
    return NULL;
}

void thr_join() {
    Pthread_mutex_lock(&m);
    while (done == 0)
        Pthread_cond_wait(&c, &m);
    Pthread_mutex_unlock(&m);
}

int main(int argc, char *argv[]) {
    printf("parent: begin\n");
    pthread_t p;
    Pthread_create(&p, NULL, child, NULL);
    thr_join();
    printf("parent: end\n");
    return 0;
}

فيه حالتين ممكن يحصلوا هنا:

  1. الـparent يجري الأول: يعمل create للـchild، ويكمل يجري هو (لو معانا processor واحد بس) وينادي على thr_join() على طول. هيمسك اللوك، يشوف إن done لسه صفر، وينوّم نفسه بـ wait() (وده بيسيب اللوك تلقائيًا). لما الـchild يجري أخيرًا، يطبع "child"، وينادي thr_exit() اللي بتمسك اللوك، تظبط done، وتعمل signal على الـparent — فيصحى. الـparent هيرجع من wait() ماسك اللوك، يسيبه، ويطبع "parent: end".
  2. الـchild يجري الأول: يظبط done = 1 على طول، وينادي signal عشان يصحّي thread نايم — لكن مفيش حد نايم أصلاً، فالـsignal مالوش أي تأثير وبترجع عادي. بعدين الـparent يجري، ينادي thr_join()، يلاقي done بقت 1، فمش بينام أصلاً وبيرجع على طول.

لاحظ إن الـparent استخدم while بدل if وهو بيفكّر يستنى ولا لأ. مش شرط منطقيًا هنا، لكنها دايمًا فكرة كويسة — وهنشوف بعد شوية ليه.

محاولات غلط — عشان تفهم أهمية كل جزء

ممكن تكون بتتساءل: هل فعلاً محتاجين متغيّر الحالة done؟ خلينا نجرب من غيره:

شكل 30.4 — محاولة غلط: من غير متغيّر حالة
void thr_exit() {
    Pthread_mutex_lock(&m);
    Pthread_cond_signal(&c);
    Pthread_mutex_unlock(&m);
}

void thr_join() {
    Pthread_mutex_lock(&m);
    Pthread_cond_wait(&c, &m);
    Pthread_mutex_unlock(&m);
}
ليه دي غلط

تخيّل إن الـchild جري فورًا ونادى thr_exit() على طول: هيعمل signal لكن مفيش thread نايم على الشرط أصلاً (لسه محدش وصل لـwait). لما الـparent يجري، هينادي wait() ببساطة ويعلق للأبد — محدش هيصحّيه تاني. من المثال ده تقدر تقدّر أهمية متغيّر الحالة done؛ هو اللي بيسجّل القيمة الفعلية اللي الـthreads مهتمة بيها. النوم والصحيان والقفل كلهم متبنيين حواليه.

وهنا محاولة غلط تانية — نتخيل إننا مش محتاجين نمسك لوك عشان نعمل signal أو wait:

شكل 30.5 — محاولة غلط: من غير لوك (كود توضيحي بس، مش حقيقي)
void thr_exit() {
    done = 1;
    Pthread_cond_signal(&c);
}

void thr_join() {
    if (done == 0)
        Pthread_cond_wait(&c);
}
race condition دقيقة

لو الـparent نادى thr_join() وشاف إن done لسه صفر، هيحاول ينام. لكن قبل ما ينادي wait() بالظبط، بيتقاطع (interrupted) والـchild يجري: بيغيّر done لـ1 وبيعمل signal — لكن مفيش حد نايم لسه فمفيش حد بيصحى. لما الـparent يرجع يجري، ينام للأبد. حزين فعلاً.

TIP: امسك اللوك دايمًا وانت بتعمل Signal

مش شرط دايمًا للصحة، لكن الأبسط والأضمن إنك تمسك اللوك وانت بتعمل signal. المثال اللي فات فيه حالة لازم فيها تمسك اللوك، وفيه حالات تانية ممكن تسيبه، بس الأفضل تتجنب ده. فببساطة: امسك اللوك وانت بتنادي signal.

العكس بالنسبة للـwait مش مجرد نصيحة — ده مفروض إجباريًا بحكم دلالة wait نفسها، لأنها دايمًا (أ) بتفترض إن اللوك متاخد وقت ما تتنده، (ب) بتسيبه وهي بتنوّم الـcaller، (ج) بترجع تاخده تاني قبل ما ترجع. يعني: امسك اللوك وانت بتنادي signal أو wait، وهتفضل مطمّن.

03 · المثال الكبير

مشكلة المنتج/المستهلك (Producer/Consumer)

المشكلة دي معروفة كمان باسم bounded buffer problem، وأول من طرحها كان Dijkstra. تخيّل كذا producer thread بتنتج قيم وتحطها في buffer، وكذا consumer thread بتاخد القيم دي من الـbuffer وتستهلكها. الترتيبة دي موجودة في أنظمة حقيقية كتير — مثلاً في web server متعدد الـthreads، producer بيحط HTTP requests في work queue، وconsumer threads بتاخدها وتعالجها. حتى لما تعمل grep foo file.txt | wc -l في الـshell، إنت بتستخدم bounded buffer فعليًا: grep هو الـproducer، wc هو الـconsumer، وبينهم UNIX pipe.

1. buffer بخانة واحدة بس

نبدأ بأبسط نسخة: خانة واحدة (int buffer) و count بيقول هي فاضية ولا لأ.

شكل 30.6 — دوال put و get — النسخة الأولى
int buffer;
int count = 0; // في الأول، فاضي

void put(int value) {
    assert(count == 0);
    count = 1;
    buffer = value;
}

int get() {
    assert(count == 1);
    count = 0;
    return buffer;
}
شكل 30.7 — threads المنتج والمستهلك — النسخة الأولى
void *producer(void *arg) {
    int i;
    int loops = (int) arg;
    for (i = 0; i < loops; i++) {
        put(i);
    }
}

void *consumer(void *arg) {
    while (1) {
        int tmp = get();
        printf("%d\n", tmp);
    }
}

2. أول محاولة (غلط): CV واحد + if

ببساطة إحاطة الكود بلوك مش كفاية هنا — محتاجين condition variable. المحاولة الأولى: CV واحد اسمه cond.

شكل 30.8 — محاولة أولى (فيها مشكلتين) — CV واحد وif
int loops; // لازم تتظبط في مكان ما...
cond_t cond;
mutex_t mutex;

void *producer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);       // p1
        if (count == 1)                    // p2
            Pthread_cond_wait(&cond, &mutex); // p3
        put(i);                             // p4
        Pthread_cond_signal(&cond);         // p5
        Pthread_mutex_unlock(&mutex);       // p6
    }
}

void *consumer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);        // c1
        if (count == 0)                     // c2
            Pthread_cond_wait(&cond, &mutex); // c3
        int tmp = get();                     // c4
        Pthread_cond_signal(&cond);          // c5
        Pthread_mutex_unlock(&mutex);        // c6
        printf("%d\n", tmp);
    }
}

مع producer واحد وconsumer واحد بس، الكود ده شغال تمام. لكن لو زوّدنا العدد (مثلاً consumer تاني)، فيه مشكلتين حرجتين. خلينا نشوف أول واحدة، وعلاقتها بالـ if قبل الـwait.

تخيّل consumer اتنين (Tc1, Tc2) وproducer واحد (Tp). Tc1 يجري الأول، يمسك اللوك، يشوف مفيش داتا، وينام. Tp يجري، يشوف الـbuffer مش مليان، يحط قيمة، وينادي signal — ده بيحرك Tc1 من النوم لطابور "جاهز" (ready)، لكنه لسه ما جريش فعليًا. Tp يكمل لفة تانية ويلاقي الـbuffer مليان فينام هو كمان. وهنا بالظبط المشكلة: consumer تاني (Tc2) بيلحق ويستهلك القيمة الوحيدة الموجودة قبل ما Tc1 يجري أصلاً! لما Tc1 يجري أخيرًا، هيرجع من wait() ويحاول ياخد قيمة — لكن مفيش قيمة خالص. الـassertion هتفشل.

السبب في المشكلة بسيط: بين لحظة ما Tp صحّى Tc1، ولحظة ما Tc1 فعليًا جري، حالة الـbuffer اتغيّرت (بسبب Tc2). يعني الـsignal مجرد "تلميح" إن حاجة اتغيّرت، مش ضمان إن الحالة لسه زي ما كانت وقت ما الـthread المصحّى هيجري فعليًا. التفسير ده لمعنى الـsignal معروف باسم Mesa semantics (نسبة لأول نظام بحثي بناها كده). في المقابل فيه Hoare semantics اللي بتضمن إن الـthread المصحّى هيجري فورًا — لكنها أصعب في البناء. تقريبًا كل نظام حقيقي موجود بيستخدم Mesa semantics.

3. أحسن، بس لسه مكسور: While بدل If

الحل لأول مشكلة سهل: نبدّل if بـ while. كده لما Tc1 يصحى، هو (وهو ماسك اللوك) بيتأكد من الشرط تاني من الأول؛ لو لقى الـbuffer لسه فاضي، بينام تاني وخلاص.

شكل 30.10 — مع While بدل If — لسه فيها مشكلة تانية
int loops;
cond_t cond;
mutex_t mutex;

void *producer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);        // p1
        while (count == 1)                  // p2  <-- if بقت while
            Pthread_cond_wait(&cond, &mutex); // p3
        put(i);                              // p4
        Pthread_cond_signal(&cond);          // p5
        Pthread_mutex_unlock(&mutex);        // p6
    }
}

void *consumer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);         // c1
        while (count == 0)                   // c2  <-- if بقت while
            Pthread_cond_wait(&cond, &mutex); // c3
        int tmp = get();                      // c4
        Pthread_cond_signal(&cond);           // c5
        Pthread_mutex_unlock(&mutex);         // c6
        printf("%d\n", tmp);
    }
}

بس لسه فيه bug تانية، وليها علاقة بإننا بنستخدم CV واحد بس. تخيّل consumer اتنين (Tc1, Tc2) بينام الاتنين الأول (مفيش داتا). Tp يجري، يحط قيمة، يصحّي واحد (يفترض Tc1). Tp بعدين يحاول يحط قيمة تانية، يلاقي البافر مليان، فينام هو كمان — دلوقتي فيه thread واحد جاهز (Tc1) وتنين نايمين (Tc2 وTp).

Tc1 يصحى، يتأكد من الشرط تاني، يلاقي فيه داتا، ياخدها، وينادي signal. بس مين هيصحّى؟ المفروض يصحّي الـproducer (لأنه هو اللي محتاج يعرف إن مكان فضي). لكن لو صحّى Tc2 بدل كده (وارد جدًا حسب إدارة طابور الانتظار)، فـTc2 هيصحى، يلاقي الـbuffer فاضي، وينام تاني. والـproducer، اللي معاه قيمة عايز يحطها، فاضل نايم للأبد. والنتيجة: الكل نايم — bug واضح.

الحل: الـsignaling لازم يبقى أكثر تحديدًا. consumer مفروض ميصحّيش consumer تاني، غير الـproducer بس — والعكس صحيح.

4. الحل: اتنين CV بدل واحد

الحل بسيط برضو: بدل CV واحد، نستخدم اتنين — واحد لكل اتجاه إشارة. Producer threads بينتظروا على empty ويعملوا signal على fill. Consumer threads بالعكس بالظبط: بينتظروا على fill ويعملوا signal على empty.

شكل 30.12 — اتنين CV بدل واحد — الحل لبافر بخانة واحدة
int loops;
cond_t empty, fill;
mutex_t mutex;

void *producer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);
        while (count == 1)
            Pthread_cond_wait(&empty, &mutex);
        put(i);
        Pthread_cond_signal(&fill);
        Pthread_mutex_unlock(&mutex);
    }
}

void *consumer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);
        while (count == 0)
            Pthread_cond_wait(&fill, &mutex);
        int tmp = get();
        Pthread_cond_signal(&empty);
        Pthread_mutex_unlock(&mutex);
        printf("%d\n", tmp);
    }
}

بالطريقة دي، المشكلة التانية بتتحل من الأساس: consumer مستحيل يصحّي consumer تاني بالغلط، وproducer مستحيل يصحّي producer تاني بالغلط — كل واحد بيصحّي النوع التاني بس.

TIP: استخدم While مش If للشروط

لما تتأكد من شرط في برنامج متعدد الـthreads، الـwhile loop دايمًا صح؛ الـif ممكن يبقى صح بس حسب دلالة الـsignaling المستخدمة. فاستخدم while دايمًا وهتفضل في أمان.

الـwhile برضو بيتعامل مع حالة الـspurious wakeups — في بعض مكتبات الـthreads، ممكن يصحى thread من غير أي signal فعلي حصل، بسبب تفاصيل في التنفيذ الداخلي. الـwhile loop بيتأكد من الشرط تاني في كل الحالات، فبيغطي الحالة دي تلقائيًا.

04 · التعميم

الحل الصحيح الكامل

عندنا دلوقتي حل شغال، لكنه مش عام (general) لسه — بافر بخانة واحدة يعني كل ما ينحط قيمة، الـproducer لازم ينام لحد ما حد ياخدها. التحسين الأخير: نزوّد عدد الخانات، بحيث كذا قيمة تتحط قبل ما ننام، وبالمثل كذا قيمة تتاخد قبل ما ننام. مع producer وconsumer واحد بس، ده بيقلل الـcontext switches؛ ومع أكتر من واحد، بيسمح فعليًا بإنتاج أو استهلاك متوازي، يعني concurrency أعلى.

التغيير الأول: شكل الـbuffer نفسه، وباستخدام مؤشرين دائريين بدل خانة واحدة:

شكل 30.13 — دوال put و get الصحيحة — buffer دائري بعدة خانات
int buffer[MAX];
int fill_ptr = 0;
int use_ptr = 0;
int count = 0;

void put(int value) {
    buffer[fill_ptr] = value;
    fill_ptr = (fill_ptr + 1) % MAX;
    count++;
}

int get() {
    int tmp = buffer[use_ptr];
    use_ptr = (use_ptr + 1) % MAX;
    count--;
    return tmp;
}

والتغيير التاني: الشروط اللي بيتأكد منها الـproducer والـconsumer قبل ما ينام أي منهم:

شكل 30.14 — الحل الكامل والصحيح لمشكلة المنتج/المستهلك
int loops;
cond_t empty, fill;
mutex_t mutex;

void *producer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);         // p1
        while (count == MAX)                 // p2
            Pthread_cond_wait(&empty, &mutex); // p3
        put(i);                               // p4
        Pthread_cond_signal(&fill);           // p5
        Pthread_mutex_unlock(&mutex);         // p6
    }
}

void *consumer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);          // c1
        while (count == 0)                    // c2
            Pthread_cond_wait(&fill, &mutex);  // c3
        int tmp = get();                       // c4
        Pthread_cond_signal(&empty);           // c5
        Pthread_mutex_unlock(&mutex);          // c6
        printf("%d\n", tmp);
    }
}

الـproducer بينام بس لو كل الخانات مليانة (count == MAX)، والـconsumer بينام بس لو كل الخانات فاضية (count == 0). وبكده اتحلت مشكلة المنتج/المستهلك بشكل كامل وعام.

05 · حالة خاصة

Covering Conditions

مثال أخير مهم، من ورقة Lampson و Redell عن نظام Pilot — نفس الفريق اللي بنى أول Mesa semantics. المشكلة بتظهر في مكتبة تخصيص ذاكرة (memory allocator) بسيطة متعددة الـthreads.

شكل 30.15 — Covering Conditions — مثال بمخصّص ذاكرة بسيط
// عدد البايتات الفاضية في الـheap
int bytesLeft = MAX_HEAP_SIZE;

// محتاجين لوك و condition variable
cond_t c;
mutex_t m;

void *allocate(int size) {
    Pthread_mutex_lock(&m);
    while (bytesLeft < size)
        Pthread_cond_wait(&c, &m);
    void *ptr = ...; // هات ميموري من الـheap
    bytesLeft -= size;
    Pthread_mutex_unlock(&m);
    return ptr;
}

void free(void *ptr, int size) {
    Pthread_mutex_lock(&m);
    // رجّع الميموري للـheap
    bytesLeft += size;
    Pthread_cond_signal(&c); // نصحي مين بالظبط؟؟
    Pthread_mutex_unlock(&m);
}

لما thread ينادي allocate()، ممكن يحتاج ينتظر لحد ما ذاكرة كفاية تتفرّج. ولما thread ينادي free()، بيعمل signal إن فيه ذاكرة أكتر بقت متاحة. المشكلة: مين بالظبط لازم يصحى؟

تخيّل مفيش ذاكرة فاضية خالص. Ta بينادي allocate(100)، وبعده Tb بينادي allocate(10). الاتنين بينامو على نفس الشرط. دلوقتي thread تالت Tc بينادي free(50). الـsignal ممكن يصحّي الغلط — لو صحّى Ta (اللي محتاج 100 بايت ومفيش كفاية لسه)، بينما Tb (اللي محتاج 10 بايت بس وفعلاً كانت هتكفيه) فاضل نايم من غير داعي.

الحل المقترح من Lampson و Redell بسيط: استبدل pthread_cond_signal() بـ pthread_cond_broadcast()، اللي بتصحّي كل الـthreads النايمة على الشرط. بكده بنضمن إن أي thread المفروض يصحى هيصحى فعلاً. العيب: تأثير سلبي محتمل على الأداء، لأننا ممكن نصحّي threads كتير مالهاش داعي تصحى دلوقتي — هتصحى، تتأكد من شرطها، ولو لسه مش متحقق تنام تاني على طول.

Lampson و Redell سمّوا الشرط ده covering condition، لأنه بيغطي كل الحالات اللي محتاجة صحيان (بطريقة متحفظة conservative). لو لقيت إن برنامجك مش شغال إلا لما تبدّل الـsignal بـbroadcast (وانت مش متوقع كده)، غالبًا عندك bug حقيقي محتاج يتصلح. لكن في حالات زي الـallocator ده، الـbroadcast فعلاً هو الحل الأبسط والمتاح.

06 · الخلاصة

الخلاصة

شفنا في الفصل ده أداة تزامن مهمة تانية غير الأقفال: condition variables. بالسماح لـthread إنه ينام لما حالة البرنامج مش زي ما هو عايز، الـCVs بتخلينا نحل مشاكل تزامن مهمة زي مشكلة المنتج/المستهلك الشهيرة، وكمان الـcovering conditions. أهم حاجة تاخدها معاك: امسك اللوك دايمًا وانت بتنادي wait أو signal، واستخدم while مش if، وفكّر كويس في عدد الـCVs اللي محتاجها حسب أنواع الـthreads اللي المفروض تتصحى.
