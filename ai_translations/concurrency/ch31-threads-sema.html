السيمافورز (Semaphores)

ملخص ومبسّط بالعامية المصرية — الفصل 31 من كتاب OSTEP (Operating Systems: Three Easy Pieces)، جزء الـ Concurrency
#concurrency #locks #condition-variables Dijkstra, 1968
31.1

السيمافور إيه أصلاً؟

لحد دلوقتي احنا اتعلمنا إن عشان تحل مشاكل concurrency كويس، محتاج حاجتين: lock (يحمي الـ critical section) وcondition variable (يخلي thread ينام لحد ما حاجة معينة تحصل). Dijkstra، من زمان، جاب فكرة اسمها semaphore — أداة واحدة بس، تقدر تستخدمها كـ lock وكمان تقدر تستخدمها كـ condition variable. يعني بدل أداتين، أداة واحدة multi-purpose.

التعريف

السيمافور هو object جواه integer، ومش بتلمس الـ integer ده مباشرة — بتتعامل معاه بس عن طريق فانكشنين:

  • sem_wait(s) — بتنقص القيمة بواحد. لو القيمة بقت أقل من صفر (negative)، الـ thread بينام (block) لحد ما حد يصحيه.
  • sem_post(s) — بتزوّد القيمة بواحد. لو فيه thread نايم مستني، بتصحي واحد منهم.

وقبل ما تستخدم أي حاجة، لازم تعمل sem_init() وتحدد الـ starting value — والقيمة دي هي اللي بتفرق كل حاجة زي ما هنشوف.

// إنشاء وتهيئة سيمافور
#include <semaphore.h>

sem_t s;
sem_init(&s, 0, 1);  // القيمة الابتدائية = 1
فكرة تساعدك تتذكر لو القيمة سالبة، القيمة دي (بالسالب) بتساوي بالظبط عدد الـ threads اللي نايمة مستنية. يعني لو القيمة -3، معناها 3 threads واقفة مستنية sem_post.
31.2

Binary Semaphore — استخدامه كـ Lock

أبسط استخدام للسيمافور إنك تخليه lock عادي. بس محتاج تسأل نفسك: القيمة الابتدائية تبقى كام؟

sem_t m;
sem_init(&m, 0, X);  // X تساوي كام؟

sem_wait(&m);
// critical section هنا
sem_post(&m);

الإجابة: X = 1. ليه؟ لأن أول واحد ينده sem_wait هينقصها لـ 0 (مش سالبة) فهيكمل يدخل الـ critical section عادي — القفل "متاح". أي حد تاني بعده هيلاقي القيمة 0، ينقصها لـ -1، فهينام.

خلينا نتفرج على المثال ده لايف: Thread 0 ماسك القفل، وThread 1 بييجي يحاول ياخده.

;; محاكاة — Two Threads Sharing One Lock

دوس "الخطوة الجاية" عشان تبدأ الـ trace.

لاحظ إن لما Thread 1 لقى القيمة سالبة، نام (Sleep) وسلّم المعالج. وبما إنه نايم، مش هيصحى إلا لما Thread 0 ينده sem_post. بسبب إن للـ lock حالتين بس (ماسك / مش ماسك)، بنسميه binary semaphore.

31.3

استخدام تاني: السيمافور للترتيب (Ordering)

مش كل استخدامات السيمافور بتبقى lock. أحيانًا عايز thread يستنى thread تاني يخلص حاجة معينة — ده بالظبط زي دور الـ condition variable. مثال كلاسيكي: أب (parent thread) عايز يستنى الابن (child thread) يخلص شغله.

sem_t s;

void *child(void *arg) {
    printf("child\n");
    sem_post(&s);       // خلصت، صحّي الأب
}

int main() {
    sem_init(&s, 0, X);   // X تساوي كام؟
    printf("parent: begin\n");
    Pthread_create(&c, NULL, child, NULL);
    sem_wait(&s);        // استنى الابن
    printf("parent: end\n");
}

هنا القيمة الابتدائية X = 0 — مختلفة عن مثال الـ lock. ليه؟ فيه احتمالين:

  • الأب يجري الأول: بينده sem_wait والقيمة لسه 0، فتنقص لـ -1 وينام. لما الابن يجري وينده sem_post، القيمة بترجع 0 ويتصحي الأب.
  • الابن يجري الأول: بينده sem_post فالقيمة تزيد لـ 1. لما الأب يجري بعدين وينده sem_wait، هيلاقيها 1، ينقصها لـ 0، ويكمل على طول من غير ما ينام خالص.

في الحالتين، النتيجة واحدة: الأب مش هيكمل قبل ما الابن يخلص.

قاعدة عامة لاختيار الـ starting value اسأل نفسك: "كام resource أنا مستعد أدّيه فورًا بعد الـ init؟" في حالة الـ lock، أنت مستعد تدي القفل (يبقى مقفول) فورًا → 1. في حالة الترتيب، مفيش حاجة جاهزة لحد ما الابن يخلص → 0.
31.4

مشكلة الـ Producer/Consumer (Bounded Buffer)

المشكلة دي كلاسيكية: عندك buffer بحجم محدود (MAX خانة)، thread اسمه producer بيحط بيانات فيه، وthread اسمه consumer بياخد البيانات ويستهلكها. لازم:

  • الـ producer ميحطش في buffer مليان.
  • الـ consumer ميقراش من buffer فاضي.

المحاولة الأولى — سيمافورين

هنستخدم سيمافورين: empty (بيتهيأ بـ MAX — يعني كل الخانات فاضية) وfull (بيتهيأ بـ 0 — مفيش حاجة مليانة لسه).

sem_t empty, full;
sem_init(&empty, 0, MAX);
sem_init(&full,  0, 0);

void *producer(void *arg) {
    for (...) {
        sem_wait(&empty);  // فيه خانة فاضية؟
        put(i);
        sem_post(&full);   // خلصت حطيت، بقى فيه حاجة مليانة
    }
}

void *consumer(void *arg) {
    while (...) {
        sem_wait(&full);   // فيه حاجة مليانة أاخدها؟
        tmp = get();
        sem_post(&empty);  // خلصت أخدت، بقى فيه خانة فاضية
    }
}

لو MAX = 1 وthread واحد من كل نوع، الحل ده شغال تمام: الـ producer بينتظر خانة فاضية، والـ consumer بينتظر حاجة مليانة، وبيتبادلوا الدور بأمان.

المشكلة الحقيقية — Race Condition

لو MAX أكبر من 1، وفيه أكتر من producer شغالين مع بعض (وأكتر من consumer)، هتظهر مشكلة: تخيل اتنين producers بينداخلوا في نفس اللحظة على put(). لو Producer A بدأ يكتب في الخانة رقم 0، وقبل ما يزوّد الـ index اتقطع، وProducer B جه وكتب هو كمان في نفس الخانة رقم 0 — البيانات اللي كتبها A ضاعت! المشكلة إن put() وget() نفسهم بيبقوا critical section، لكن السيمافورين اللي فوق (empty/full) مش بيحموهم من بعض.

محاولة إصلاح — لكن غلط: Deadlock

الحل البديهي: ضيف mutex يلف حوالين كل حاجة، من أول sem_wait(empty) لحد آخر sem_post(full). المشكلة إن ده بيسبب deadlock. تخيل الآتي: الـ consumer بيمسك الـ mutex الأول، وبعدين بينده sem_wait(full) — لكن مفيش حاجة مليانة لسه، فهينام... وهو لسه ماسك الـ mutex! دلوقتي الـ producer عايز يحط بيانات ويصحي الـ consumer، بس عشان يعمل كده لازم الأول ياخد نفس الـ mutex — واللي مقفول. الاتنين واقفين مستنيين بعض للأبد.

قاعدة مهمة متحطّش mutex حوالين كود ممكن ينده sem_wait على سيمافور تاني ممكن يخليه ينام — وهو لسه ماسك القفل. القفل ده هيفضل ماسكه وهو نايم، وكل حد محتاج القفل عشان يصحّيه هيتقفل عليه.

الحل الصح — ضيّق نطاق الـ mutex

الحل: خلي الـ mutex يلف بس حوالين الجزء اللي فعلاً بيلمس الـ buffer (الـ put/get)، مش حوالين استدعاءات empty/full.

void *producer(void *arg) {
    for (...) {
        sem_wait(&empty);
        sem_wait(&mutex);   // قفل ضيق
        put(i);
        sem_post(&mutex);   // فك القفل
        sem_post(&full);
    }
}

void *consumer(void *arg) {
    while (...) {
        sem_wait(&full);
        sem_wait(&mutex);
        tmp = get();
        sem_post(&mutex);
        sem_post(&empty);
    }
}

دلوقتي مفيش thread ممكن ينام وهو ماسك الـ mutex، فالـ deadlock اتحل. الـ pattern ده (bounded buffer) شائع جدًا في برمجة الـ threads — يستاهل تفهمه كويس.

31.5

Reader-Writer Locks

أحيانًا مش كل الوصول لـ data structure لازم يبقى exclusive. مثلاً list فيها عمليات insert (بتغيّر البيانات) وعمليات lookup (بس بتقرأ). طول ما مفيش insert شغال، ممكن كذا lookup يشتغلوا مع بعض من غير مشاكل. عشان كده فيه lock خاص اسمه reader-writer lock:

  • أي عدد من الـ readers يقدروا يدخلوا مع بعض في نفس الوقت.
  • الـ writer لازم يبقى لوحده تمامًا — مفيش reader ولا writer تاني وقتها.

الفكرة في التنفيذ: فيه عداد readers محمي بـ lock عادي، وفيه سيمافور اسمه writelock. أول reader بيدخل هو اللي بيمسك الـ writelock (عشان يمنع أي writer يدخل)، وآخر reader بيخرج هو اللي بيسيبه. الـ writer نفسه بس بيمسك الـ writelock مباشرة زي أي lock عادي.

void rwlock_acquire_readlock(rwlock_t *rw) {
    sem_wait(&rw->lock);
    rw->readers++;
    if (rw->readers == 1)          // أول reader
        sem_wait(&rw->writelock);  // يقفل على الـ writers
    sem_post(&rw->lock);
}

void rwlock_release_readlock(rwlock_t *rw) {
    sem_wait(&rw->lock);
    rw->readers--;
    if (rw->readers == 0)          // آخر reader
        sem_post(&rw->writelock); // يفتح للـ writers
    sem_post(&rw->lock);
}
عيب مهم الحل ده سهل الـ starvation للـ writers — لو فيه readers مستمرين يدخلوا واحد ورا التاني، الـ writer ممكن يفضل مستني للأبد. وفوق كده، reader-writer locks عمومًا بتضيف overhead، فمش دايمًا أسرع من lock عادي بسيط. القاعدة: ابدأ بالحل البسيط، ومتعقدش غير لو محتاج فعلاً.
31.6

مشكلة الفلاسفة الخمسة (Dining Philosophers)

مشكلة شهيرة من Dijkstra — مش عملية جدًا لكنها بتتسأل كتير في الـ interviews. الإعداد: 5 فلاسفة حوالين طاولة دائرية، وبينهم 5 شوك (شوكة بين كل اتنين). كل فيلسوف عشان ياكل محتاج الشوكة اللي شماله والشوكة اللي يمينه سوا.

الحل الغلط

كل فيلسوف يمسك شوكة شماله الأول، وبعدين شوكة يمينه:

void get_forks(int p) {
    sem_wait(&forks[left(p)]);
    sem_wait(&forks[right(p)]);
}

لو الخمسة فلاسفة مسكوا الشوكة اللي شمالهم في نفس اللحظة، كل واحد فيهم هيبقى ماسك شوكة واحدة بس ومستني الشوكة التانية اللي واحد جنبه ماسكها — deadlock دائري بين الخمسة.

الحل — كسر الحلقة (Break the Cycle)

الحل البسيط: خلي فيلسوف واحد بس (آخر واحد، رقم 4 مثلاً) ياخد الشوك بترتيب معكوس — يمين الأول، بعدين شمال:

void get_forks(int p) {
    if (p == 4) {                    // الاستثناء
        sem_wait(&forks[right(p)]);
        sem_wait(&forks[left(p)]);
    } else {
        sem_wait(&forks[left(p)]);
        sem_wait(&forks[right(p)]);
    }
}

بكده مفيش سيناريو ممكن كل الفلاسفة الخمسة يمسكوا شوكة واحدة ويستنوا بعض في نفس الوقت — الحلقة اتكسرت، والـ deadlock مبقاش ممكن يحصل.

31.7

Thread Throttling

استخدام تاني عملي جدًا: لو عندك مئات الـ threads شغالين مع بعض، وفيه جزء من الكود بياخد memory كتير — لو كل الـ threads دخلوا الجزء ده مع بعض في نفس اللحظة، الجهاز ممكن يعدي الـ physical memory المتاحة ويبدأ thrashing (swap مستمر) والأداء يقف تمامًا.

الحل بسيط: سيمافور بتهيّئه بأقصى عدد threads مسموح لهم يدخلوا الجزء الخطير ده في نفس الوقت، وتحط sem_wait/sem_post حواليه. بكده انت بتتحكم (throttle) في عدد الـ threads المتزامنة اللي بتاخد الموارد الحساسة دي — ده بيتسمى admission control.

31.8

وإزاي تبني سيمافور بنفسك؟

ده حلو: تقدر تبني السيمافور نفسه من الأدوات الأساسية اللي اتعلمتها قبل كده — lock واحد وcondition variable واحد وinteger بيحمل القيمة. الكتاب بيسميها بمزاح Zemaphore.

typedef struct {
    int value;
    pthread_cond_t  cond;
    pthread_mutex_t lock;
} Zem_t;

void Zem_wait(Zem_t *s) {
    Mutex_lock(&s->lock);
    while (s->value <= 0)
        Cond_wait(&s->cond, &s->lock);  // نام واستنى
    s->value--;
    Mutex_unlock(&s->lock);
}

void Zem_post(Zem_t *s) {
    Mutex_lock(&s->lock);
    s->value++;
    Cond_signal(&s->cond);            // صحّي واحد نايم
    Mutex_unlock(&s->lock);
}

فرق بسيط عن سيمافور Dijkstra الأصلي: هنا القيمة مبتنزلش تحت الصفر خالص (يعني مش بنحافظ على الـ invariant بتاع "القيمة السالبة = عدد المنتظرين"). ده أسهل في التنفيذ، وده فعليًا اللي بيحصل في Linux الحالي.

حاجة تستاهل تفكر فيها عكس كده — بناء condition variable من سيمافور — أصعب بكتير مما يبدو. حتى مبرمجين محترفين جربوا كده في بيئة Windows ووقعوا في bugs كتير. جرب بنفسك وفكر ليه الاتجاه ده أصعب.
31.9

الخلاصة

السيمافور أداة قوية ومرنة — لدرجة إن بعض المبرمجين بيستخدموها بس، ومش بيحتاجوا locks أو condition variables منفصلين خالص. اللي شفناه هنا كان بس شوية أمثلة كلاسيكية (lock، ordering، bounded buffer، reader-writer، dining philosophers، throttling) — لكن الفكرة الأساسية واحدة في كل مكان: sem_wait بينقص ويستنى لو القيمة سالبة، وsem_post بيزود ويصحّي حد لو محتاج.

لو عايز تتمرن أكتر، فيه كتاب مجاني اسمه "The Little Book of Semaphores" لـ Allen Downey فيه تمارين كتير على نفس الفكرة.
