هياكل البيانات المتزامنة القائمة على الأقفال

Lock-based Concurrent Data Structures

لما يبقى عندك أكتر من thread عايزين يوصلوا لنفس الـ data structure في نفس الوقت، إزاي تحط الأقفال بحيث الكود يفضل صح (correct) وفي نفس الوقت سريع (fast)؟ الفصل ده بياخدنا في رحلة من عداد بسيط لحد جدول hash كامل، ويوضح إن "أضف قفل واحد وخلاص" حل شغال، بس مش دايمًا الحل الأمثل.

01 · البداية

المقدمة والتحدي

إضافة lock لأي data structure عشان تخليه thread-safe مش صعبة في حد ذاتها — بتاخد لوك قبل ما تلمس الـstructure، وتسيبه بعد ما تخلص. اللي صعب فعلاً هو إنك تحط الأقفال دي بطريقة تدّيك حاجتين مع بعض: Correctness (الكود يشتغل صح مهما كان عدد الـthreads اللي بتنافس على نفس البيانات)، وPerformance (كذا thread يقدروا يشتغلوا فعلاً في نفس الوقت من غير ما يقعدوا يستنوا بعض طول الوقت).

CRUX: إزاي نضيف أقفال لهياكل البيانات؟

لما يكون عندنا data structure معينة، إزاي نضيف الأقفال بحيث تشتغل صح؟ وأهم من كده، إزاي نضيفها بحيث الـstructure تدّي أداء عالي، وتسمح لكذا thread يوصلوا لها في نفس الوقت (concurrently)؟

الموضوع ده اتبحث فيه علميًا لسنين طويلة وفيه آلاف الأبحاث عنه، فمستحيل نغطي كل حاجة في فصل واحد. اللي هنعمله هنا إننا نمشي على أربع أمثلة كلاسيكية — عداد، قائمة مرتبطة، طابور، جدول hash — ونشوف إزاي فكرة "لوك واحد بسيط" بتتطور لحلول أذكى لما الأداء يبقى مشكلة حقيقية.

Thread-safeالكود يشتغل صح حتى لو كذا thread بينفذوه في نفس الوقت على نفس البيانات.
Critical Sectionالجزء من الكود اللي بيلمس بيانات مشتركة، ولازم يتنفذ من thread واحد بس في كل لحظة.
Contentionلما كذا thread يتزاحموا على نفس الـlock، فيقعدوا يستنوا بعض بدل ما يشتغلوا.
Scalabilityقدرة الكود إنه يفضل سريع حتى لو زوّدنا عدد الـthreads/الـCPUs اللي بتشتغل.
02 · أبسط مثال

العدادات المتزامنة (Concurrent Counters)

1. العداد البسيط — بدون أي تزامن

أبسط حاجة ممكن نبدأ بيها: عداد عادي، عبارة عن int واحد جوه struct، وأربع دوال (init / increment / decrement / get) كل واحدة بتلمس القيمة دي مباشرة. بسيط جدًا، بس لو استخدمته من كذا thread في نفس الوقت هتقع في race condition: عملية c->value++ مش عملية واحدة (atomic) فعليًا — هي في الحقيقة قراءة، زيادة، وكتابة، وممكن تحصل مقاطعة (interleaving) بين thread وتاني تخلي تحديث يضيع.

شكل 29.1 — عداد عادي من غير أي قفل
typedef struct __counter_t {
    int value;
} counter_t;

void init(counter_t *c) {
    c->value = 0;
}

void increment(counter_t *c) {
    c->value++;
}

void decrement(counter_t *c) {
    c->value--;
}

int get(counter_t *c) {
    return c->value;
}

2. خليه Thread-Safe — قفل واحد وخلاص

الحل الأول والأبسط: نضيف pthread_mutex_t lock جوه الـstruct، ونحوط كل عملية بتلمس value بـ lock وunlock. الشكل ده بيفكرك بـ monitors: تاخد اللوك أول ما تدخل الدالة، وتسيبه قبل ما تخرج منها.

شكل 29.2 — نفس العداد لكن بلوك واحد يحمي كل عملية
typedef struct __counter_t {
    int value;
    pthread_mutex_t lock;
} counter_t;

void init(counter_t *c) {
    c->value = 0;
    Pthread_mutex_init(&c->lock, NULL);
}

void increment(counter_t *c) {
    Pthread_mutex_lock(&c->lock);
    c->value++;
    Pthread_mutex_unlock(&c->lock);
}

void decrement(counter_t *c) {
    Pthread_mutex_lock(&c->lock);
    c->value--;
    Pthread_mutex_unlock(&c->lock);
}

int get(counter_t *c) {
    Pthread_mutex_lock(&c->lock);
    int rc = c->value;
    Pthread_mutex_unlock(&c->lock);
    return rc;
}

دلوقتي الكود صحيح 100% ولا فيه أي race condition. المشكلة الجاية مش في الصحة — المشكلة في الأداء.

3. المشكلة: العداد ده مبيتوسّعش (Doesn't Scale)

لو شغّلت benchmark بسيط — كل thread يعمل increment للعداد مليون مرة، وغيّرت عدد الـthreads من واحد لأربعة على جهاز بـ4 كور — هتلاقي حاجة غريبة: thread واحد بياخد وقت صغير جدًا (حوالي 0.03 ثانية) عشان يخلّص المليون تحديث. لكن ثنين threads بيشتغلوا في نفس الوقت، كل واحد بيعمل مليون update، بياخدوا مع بعض أكتر من 5 ثواني! وكل ما تزوّد threads بيبقى الموضوع أسوأ.

ده عكس اللي إحنا عايزينه. المثالي (perfect scaling) إن الوقت يفضل تقريبًا زي ما هو حتى لو زوّدنا عدد الـthreads، لأن الشغل بيتوزّع على processors مختلفة. المشكلة هنا إن الـlock الواحد بقى bottleneck: كل الـthreads بتتخانق على نفس اللوك بالظبط، فبتقعد تستنى بعض (contention عالي جدًا) بدل ما تشتغل فعلاً بالتوازي.

4. الحل: العداد التقريبي (Approximate Counter)

الفكرة الذكية هنا: بدل ما يكون فيه عداد logical واحد بس بيتشارك فيه الكل، نعمل عداد local منفصل لكل CPU core، + عداد global واحد. يعني على جهاز بـ4 كور، هيبقى فيه 4 عدادات محلية (L1..L4) وعداد عالمي واحد (G)، وكل عداد محلي ليه لوك خاص بيه (llock)، وفيه لوك تاني منفصل للعالمي (glock).

لما thread شغّال على core معيّن يعمل increment، هو بيزوّد العداد المحلي بتاعه بس، وده محمي بلوك محلي رخيص. وبما إن كل core بيحدّث عداده الخاص، الـthreads اللي شغالة على كورز مختلفة أصلاً مش بتتخانق على نفس اللوك — فالتحديثات دي scalable من الأساس.

بس عشان نقدر نعرف القيمة الإجمالية وقت ما حد يعمل get()، لازم بين كل فترة والتانية ننقل قيمة العداد المحلي للعالمي: ناخد الـglobal lock، نزوّد الـglobal بقد قيمة الـlocal، وبعدين نصفّر الـlocal. الانتقال ده بيحصل لما العداد المحلي يوصل threshold معيّن اسمه S.

S هو اللي بيتحكم في الـtrade-off بين الدقة والسرعة:

  • S صغير → كل تحديث تقريبًا بيروح على طول للـglobal → دقة عالية، لكن أداء زي العداد العادي بالظبط.
  • S كبير → scalability عالية جدًا (تحديثات محلية كتير من غير ما نلمس الـglobal lock)، لكن قيمة الـglobal ممكن تبعد عن الحقيقة بمقدار (عدد الـCPUs × S) كحد أقصى.

(تقدر برضو تاخد كل اللوكس — المحلية والعالمية — بترتيب معيّن (عشان تتفادى deadlock) وتجيب قيمة دقيقة 100%، لكن ده مش scalable خالص.)

الكود الكامل للعداد التقريبي

شكل 29.4 — تنفيذ العداد التقريبي بعدادات محلية + عالمي
typedef struct __counter_t {
    int global;                  // القيمة العالمية (global count)
    pthread_mutex_t glock;       // لوك العالمي (global lock)
    int local[NUMCPUS];          // عداد محلي لكل CPU
    pthread_mutex_t llock[NUMCPUS]; // ولوك محلي لكل واحد فيهم
    int threshold;                // كل قد ايه ننقل للـglobal
} counter_t;

// init: نسجل الـthreshold، نظبط كل اللوكس،
// ونصفر كل القيم المحلية والعالمية
void init(counter_t *c, int threshold) {
    c->threshold = threshold;
    c->global = 0;
    pthread_mutex_init(&c->glock, NULL);
    int i;
    for (i = 0; i < NUMCPUS; i++) {
        c->local[i] = 0;
        pthread_mutex_init(&c->llock[i], NULL);
    }
}

// update: في الغالب بناخد بس اللوك المحلي ونحدث
// القيمة المحلية؛ لو وصلت للـ threshold، ناخد
// اللوك العالمي وننقل القيمة المحلية عليه
void update(counter_t *c, int threadID, int amt) {
    int cpu = threadID % NUMCPUS;
    pthread_mutex_lock(&c->llock[cpu]);
    c->local[cpu] += amt;
    if (c->local[cpu] >= c->threshold) {
        // ننقلها للعالمي (بنفترض amt موجبة)
        pthread_mutex_lock(&c->glock);
        c->global += c->local[cpu];
        pthread_mutex_unlock(&c->glock);
        c->local[cpu] = 0;
    }
    pthread_mutex_unlock(&c->llock[cpu]);
}

// get: بترجع القيمة العالمية بس (تقريبية!)
int get(counter_t *c) {
    pthread_mutex_lock(&c->glock);
    int val = c->global;
    pthread_mutex_unlock(&c->glock);
    return val; // approximate بس
}

خلينا نمشي على الكود سطر سطر: الـstruct فيها global والقفل بتاعه glock، وبعدين array من العدادات المحلية local[NUMCPUS] مع array تاني من اللوكس llock[NUMCPUS]، وأخيرًا threshold. دالة init بترتب كل ده وتصفّر القيم. دالة update هي قلب الفكرة: بتحدد الـCPU المناسب (threadID % NUMCPUS)، تاخد لوكه المحلي، تزوّد قيمته، ولو وصلت للـthreshold تاخد الـglobal lock وتنقل القيمة وتصفّر المحلي. دالة get بترجع بس قيمة الـglobal الحالية — وهي، زي ما اتفقنا، تقريبية مش دقيقة.

نتيجة القياس الفعلي في الكتاب مبهرة: العداد التقريبي بـS = 1024 بيخلّص 4 مليون update على 4 processors في وقت قريب جدًا من وقت مليون update على processor واحد بس — يعني scaling شبه مثالي. وكل ما زوّدت S الأداء بيتحسن أكتر، على حساب دقة القيمة العالمية.

TIP: زيادة التزامن مش شرط تبقى أسرع

لو الطريقة اللي بتصممها فيها overhead كبير — زي إنك تاخد وتسيب لوكس كتير أوي بدل مرة واحدة — فحقيقة إنها "أكتر تزامنًا" مش لازم تبقى مفيدة. السكيمات البسيطة غالبًا بتشتغل كويس، خصوصًا لو الروتينات المكلفة نادرة الحدوث. زيادة الأقفال والتعقيد ممكن تبقى وبال عليك. الطريقة الوحيدة إنك تتأكد بجد: تبني الاتنين (البسيط والمعقد) وتقيسهم فعليًا performance-wise — مفيش تحايل على القياس.

03 · تركيبة أعقد

القوائم المرتبطة المتزامنة (Concurrent Linked Lists)

نطلع درجة في التعقيد: القائمة المرتبطة. عشان نبسّط الموضوع، هنركّز بس على insert وlookup، ونسيب الـdelete وغيرها كتمرين للقارئ.

1. النسخة الأساسية

زي ما اتعودنا: node فيها key و pointer للـ next، والقائمة نفسها فيها head ولوك واحد. الـList_Insert بياخد اللوك من أول لحظة، يعمل malloc لعقدة جديدة، ولو الـmalloc فشلت (حالة نادرة لكن ممكنة) لازم يسيب اللوك قبل ما يرجع بالخطأ — وإلا هيفضل اللوك متاخد للأبد وأي thread تاني هيعلّق (deadlock).

شكل 29.7 — قائمة مرتبطة متزامنة — النسخة الأولى
// شكل الـnode الأساسي
typedef struct __node_t {
    int key;
    struct __node_t *next;
} node_t;

// شكل القائمة نفسها (وحدة واحدة لكل list)
typedef struct __list_t {
    node_t *head;
    pthread_mutex_t lock;
} list_t;

void List_Init(list_t *L) {
    L->head = NULL;
    pthread_mutex_init(&L->lock, NULL);
}

int List_Insert(list_t *L, int key) {
    pthread_mutex_lock(&L->lock);
    node_t *new = malloc(sizeof(node_t));
    if (new == NULL) {
        perror("malloc");
        pthread_mutex_unlock(&L->lock);
        return -1; // فشل
    }
    new->key = key;
    new->next = L->head;
    L->head = new;
    pthread_mutex_unlock(&L->lock);
    return 0; // نجاح
}

int List_Lookup(list_t *L, int key) {
    pthread_mutex_lock(&L->lock);
    node_t *curr = L->head;
    while (curr) {
        if (curr->key == key) {
            pthread_mutex_unlock(&L->lock);
            return 0; // لقيناه
        }
        curr = curr->next;
    }
    pthread_mutex_unlock(&L->lock);
    return -1; // مش موجود
}
تنبيه: مسارات الأخطاء خطيرة

التعامل مع الـcontrol flow الاستثنائي زي ده (فشل الـmalloc) اتّبت إنه error-prone جدًا في الواقع. دراسة على تعديلات Linux kernel لقت إن نسبة كبيرة من الـbugs (قريب من 40%) بتحصل بالظبط في المسارات النادرة دي — يعني اللي مش بتتنفذ غالبًا وبالتالي مش بتتاختبر كويس.

2. النسخة المحسّنة — إعادة ترتيب بسيطة

السؤال: نقدر نعيد كتابة الدالتين بحيث يفضلوا صح مع التزامن، لكن من غير ما نضطر نحط unlock في كل مسار فشل ممكن؟ الإجابة: أيوه.

في List_Insert: عملية الـmalloc نفسها مش محتاجة حماية أصلاً — طالما malloc نفسها thread-safe، كل thread يقدر ينده عليها من غير خوف من race condition. فبنعمل الـmalloc الأول من غير أي لوك، وبعدين لما نيجي فعلاً نعدّل على القائمة المشتركة (نربط العقدة الجديدة بالـhead) وقتها بس ناخد اللوك — يعني اللوك بيحوط الـcritical section الفعلي بس مش الدالة كلها.

في List_Lookup: بدل ما يكون فيه أكتر من return جوه اللوب (وبالتالي أكتر من مكان لازم تعمل فيه unlock)، بنستخدم متغير واحد rv وبنعمل break من اللوب لما نلاقي الـkey، وبنسيب اللوك مرة واحدة بس في نهاية الدالة قبل الـreturn. النتيجة: أماكن أقل للـlock/unlock في الكود، وبالتالي احتمال أقل إنك تنسى تسيب لوك بالغلط.

شكل 29.8 — القائمة بعد إعادة الترتيب — لوك بيحوط الـcritical section بس
void List_Init(list_t *L) {
    L->head = NULL;
    pthread_mutex_init(&L->lock, NULL);
}

int List_Insert(list_t *L, int key) {
    // الجزء ده مش محتاج تزامن أصلاً
    node_t *new = malloc(sizeof(node_t));
    if (new == NULL) {
        perror("malloc");
        return -1;
    }
    new->key = key;
    // اللوك حوالين الـcritical section بس
    pthread_mutex_lock(&L->lock);
    new->next = L->head;
    L->head = new;
    pthread_mutex_unlock(&L->lock);
    return 0; // نجاح
}

int List_Lookup(list_t *L, int key) {
    int rv = -1;
    pthread_mutex_lock(&L->lock);
    node_t *curr = L->head;
    while (curr) {
        if (curr->key == key) {
            rv = 0;
            break;
        }
        curr = curr->next;
    }
    pthread_mutex_unlock(&L->lock);
    return rv; // نجاح أو فشل، مخرج واحد بس
}
TIP: احترس من الأقفال وتغييرات الـcontrol flow

نصيحة عامة، مش بس في الكود المتزامن: احترس من أي تغيير في مسار التنفيذ بيؤدي لـ return أو exit أو أي حالة خطأ توقف تنفيذ الدالة. لأن كتير من الدوال بتبدأ بأخذ لوك أو حجز memory أو أي عملية stateful تانية، فلما يحصل error لازم الكود "يرجّع" كل الحالة دي قبل ما يخرج — وده سهل جدًا تغلط فيه. الأفضل تصمم الكود من الأساس بحيث يقلل الأنماط دي قد الإمكان.

3. Hand-over-hand Locking (Lock Coupling)

القائمة اللي فوق دي شغالة، لكن برضو مش scalable لأنها لسه بتستخدم لوك واحد للقائمة كلها. فكرة تانية استكشفها الباحثين: بدل لوك واحد للقائمة، تحط لوك لكل node. وانت ماشي (traversing) في القائمة، الكود بياخد لوك الـnode الجاية الأول، وبعدين يسيب لوك الـnode الحالية — يعني "إيد ورا إيد" (ومن هنا الاسم hand-over-hand).

نظريًا الفكرة معقولة جدًا وبتسمح بتزامن عالي في عمليات القائمة. لكن عمليًا، صعب جدًا توصّل الطريقة دي تبقى أسرع من اللوك الواحد البسيط — overhead إنك تاخد وتسيب لوك لكل node وانت بتعدّي على قائمة كبيرة بيبقى مكلف جدًا. حتى مع قوائم كبيرة وعدد threads كبير، مش غالبًا هتلاقي hand-over-hand أسرع من لوك واحد بسيط. يمكن حل وسط (hybrid) — تاخد لوك جديد كل كام node بدل كل node لوحده — يستاهل تجربة.

04 · لوكين بدل واحد

الطوابير المتزامنة (Concurrent Queues)

زي ما اتعودنا، الطريقة الافتراضية دايمًا موجودة: حط big lock واحد وخلاص. هنا هنتخطاها ونشوف طريقة أذكى صمّمها Michael and Scott.

الفكرة: بدل لوك واحد للطابور كله، فيه اتنين — واحد للـ head (اسمه head_lock) وواحد للـtail (اسمه tail_lock). كده عملية Enqueue (بتحط في الآخر) بتستخدم غالبًا tail_lock بس، وعملية Dequeue (بتشيل من الأول) بتستخدم head_lock بس — فالاتنين ممكن يحصلوا في نفس الوقت من غير ما يتصادموا خالص.

الحيلة الذكية اللي استخدمها Michael and Scott: إضافة dummy node وهمية وقت الـinit. من غيرها، أول عملية enqueue أو dequeue هتحتاج تلمس الـhead والـtail مع بعض، وده كان هيرجّعنا للوك واحد مشترك. بوجود الـdummy، فصل الـhead عن الـtail بقى ممكن فعليًا.

شكل 29.9 — طابور Michael and Scott — لوك للـhead ولوك للـtail
typedef struct __node_t {
    int value;
    struct __node_t *next;
} node_t;

typedef struct __queue_t {
    node_t *head;
    node_t *tail;
    pthread_mutex_t head_lock, tail_lock;
} queue_t;

void Queue_Init(queue_t *q) {
    node_t *tmp = malloc(sizeof(node_t));
    tmp->next = NULL;
    q->head = q->tail = tmp;   // عقدة وهمية (dummy)
    pthread_mutex_init(&q->head_lock, NULL);
    pthread_mutex_init(&q->tail_lock, NULL);
}

void Queue_Enqueue(queue_t *q, int value) {
    node_t *tmp = malloc(sizeof(node_t));
    assert(tmp != NULL);
    tmp->value = value;
    tmp->next = NULL;

    pthread_mutex_lock(&q->tail_lock);
    q->tail->next = tmp;
    q->tail = tmp;
    pthread_mutex_unlock(&q->tail_lock);
}

int Queue_Dequeue(queue_t *q, int *value) {
    pthread_mutex_lock(&q->head_lock);
    node_t *tmp = q->head;
    node_t *new_head = tmp->next;
    if (new_head == NULL) {
        pthread_mutex_unlock(&q->head_lock);
        return -1; // الطابور فاضي
    }
    *value = new_head->value;
    q->head = new_head;
    pthread_mutex_unlock(&q->head_lock);
    free(tmp);
    return 0;
}

خلينا نمشي على الكود: Queue_Init بتعمل malloc لعقدة dummy وتخلي head وtail الاتنين يشاوروا عليها. Queue_Enqueue بتاخد tail_lock بس، تربط tail->next بالعقدة الجديدة، وتحرك tail عليها. Queue_Dequeue بتاخد head_lock بس، تشوف لو الطابور فاضي (new_head == NULL) ترجع -1، وإلا تاخد القيمة من new_head، تحرك head، وتعمل free للعقدة القديمة.

ملاحظة مهمة: الطابور ده بلوكس بس — مفيهوش آلية "استنى لو الطابور فاضي" أو "استنى لو ممتلئ". الموضوع ده (bounded buffer) هو محور الفصل الجاي عن condition variables.

05 · أعلى تزامن ممكن هنا

جدول الـHash المتزامن (Concurrent Hash Table)

آخر مثال، وهو أبسط حاجة وأقواها في نفس الوقت: hash table بسيط (من غير resizing — سايبينها تمرين للقارئ). الفكرة قائمة بالكامل على القوائم المرتبطة اللي عملناها فوق.

السبب في أدائه الممتاز: بدل ما يكون فيه لوك واحد للجدول كله، بيتحط لوك مستقل لكل bucket (وكل bucket نفسه عبارة عن list_t زي اللي بنيناها). كده كذا thread يقدروا يشتغلوا على buckets مختلفة في نفس الوقت من غير ما يستنوا بعض خالص.

شكل 29.10 — جدول hash مبني فوق القوائم المتزامنة، بـ101 bucket
#define BUCKETS (101)

typedef struct __hash_t {
    list_t lists[BUCKETS];
} hash_t;

void Hash_Init(hash_t *H) {
    int i;
    for (i = 0; i < BUCKETS; i++)
        List_Init(&H->lists[i]);
}

int Hash_Insert(hash_t *H, int key) {
    return List_Insert(&H->lists[key % BUCKETS], key);
}

int Hash_Lookup(hash_t *H, int key) {
    return List_Lookup(&H->lists[key % BUCKETS], key);
}

الكود بسيط جدًا: Hash_Init بتعمل List_Init لكل bucket في المصفوفة. Hash_Insert وHash_Lookup بس بيحسبوا key % BUCKETS عشان يحددوا هو في أنهي bucket، وبعدين ينادوا على List_Insert/List_Lookup اللي عملناها في القسم اللي فات.

النتيجة في القياس الفعلي: جدول الـhash ده بيتوسّع (scale) بشكل رهيب — الفرق واضح جدًا لما تقارنه بقائمة مرتبطة عادية بلوك واحد، اللي مبتتوسعش خالص مهما زوّدت الـthreads.

06 · الخلاصة

الخلاصة والدروس المستفادة

شفنا في الفصل ده أربع هياكل بيانات متزامنة — من العداد، للقائمة، للطابور، لحد جدول الـhash المستخدم في كل حتة. أهم الدروس اللي طلعنا بيها:

  • احترس جدًا وانت بتاخد/تسيب لوكس حوالين أي تغيير في الـcontrol flow (زي مسارات الأخطاء).
  • زيادة التزامن (concurrency) مش شرط تبقى معناها أداء أحسن — أحيانًا بتكون العكس.
  • معالجة مشاكل الأداء لازم تكون لما توجد فعلاً، مش استباقًا.
TIP: تجنّب التحسين المبكر (Knuth's Law)

لما تبني data structure متزامنة، ابدأ بأبسط طريقة ممكنة — لوك واحد كبير يحمي كل حاجة. بالطريقة دي هتبني حاجة صحيحة من البداية؛ ولو بعدين لقيت فعلاً مشكلة أداء، وقتها بس حسّنها. زي ما قال Knuth: "التحسين المبكر هو أصل كل الشرور".

تاريخيًا، أنظمة زي SunOS و Linux لما بدأت تشتغل على multiprocessors استخدمت لوك واحد كبير. في Linux كان اسمه بالظبط Big Kernel Lock (BKL). الطريقة دي شغالة كويس لسنين طويلة، لحد ما أنظمة الـmulti-core بقت الأساس وبقى اللوك الواحد ده bottleneck حقيقي. Linux حلها بطريقة مباشرة: استبدل اللوك الواحد بلوكسات كتير. أما Sun فقررت حاجة أكبر بكتير: بنت نظام تشغيل جديد بالكامل من الصفر اسمه Solaris، مصمم من أول يوم يراعي الـconcurrency في بنيته الأساسية.

07 · تطبيق عملي

أسئلة الواجب

الفصل بيقترح واجب عملي بالكامل قائم على إنك تكتب كود متزامن حقيقي وتقيس أداءه — مهارة أساسية جدًا لأي حد بيتعلم backend/systems programming.

ابدأ بإعادة القياسات اللي في الفصل بنفسك — استخدم gettimeofday() عشان تقيس الوقت. جرّب تعرف دقة الـtimer ده، وأصغر فترة زمنية يقدر يقيسها.
ابنِ عداد متزامن بسيط (زي الشكل 29.2)، وقيس الوقت اللي بياخده لما تزوّد عدد الـthreads. كام CPU متاح عندك؟ هل ده بيأثر على القياسات؟
ابنِ نسخة من العداد التقريبي، وقيس أداءه مع تغيير عدد الـthreads والـthreshold. هل الأرقام اللي بتطلعلك قريبة من اللي في الفصل؟
ابنِ قائمة مرتبطة بتستخدم hand-over-hand locking. اقرأ الورقة البحثية بتاعتها الأول عشان تفهم الفكرة كويس، وبعدين قيس أداءها مقابل القائمة العادية.
اختار data structure تانية تحبها (زي B-tree)، وابدأ بلوك واحد بسيط، وقيس أداءها مع زيادة عدد الـthreads.
فكّر في استراتيجية locking أذكى لنفس الـdata structure اللي اخترتها، وقارن أداءها بالطريقة البسيطة.
