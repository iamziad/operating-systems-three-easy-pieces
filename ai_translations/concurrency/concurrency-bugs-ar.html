Common Concurrency Problems

شرح مفصّل بالعربي المصري لأشهر أنواع الـ bugs اللي بتظهر في البرامج اللي فيها أكتر من thread شغالين مع بعض: من الـ non-deadlock bugs البسيطة، لحد الـ deadlock بكل أسبابه وطرق التعامل معاه.

الباحثين مهتمين بموضوع الـ concurrency bugs من زمان، وأكتر حاجة اتدرست بعمق هي الـ deadlock. بس في السنين الأخيرة، بقى فيه اهتمام أكبر بدراسة أنواع تانية من البgs اللي مالهاش علاقة بالـ deadlock خالص. في الشابتر ده هناخد جولة على أشهر أنواع المشاكل دي، عشان تبقى عارف تدور على إيه لما تكتب كود concurrent.

السؤال الأساسي

إزاي نتعامل مع الـ concurrency bugs الشائعة؟ الـ bugs دي بتيجي في أنماط متكررة، وأول خطوة عشان تكتب كود صحيح ومتين إنك تعرف الأنماط دي وتحسّها وهي جاية.

١. Non-Deadlock Bugs

النوع ده هو الأكتر شيوعًا حسب الدراسة. Lu وزمايلها لقوا إن أغلب الـ non-deadlock bugs بترجع لنوعين رئيسيين: Atomicity Violation و Order Violation. الحلو في النوع ده إنه غالبًا أسهل في الإصلاح من الـ deadlock.

Atomicity Violation

التعريف الرسمي: بيحصل لما يكون فيه سلسلة من الوصول للذاكرة (memory accesses) المفروض تتنفذ كوحدة واحدة (atomic)، لكن فعليًا مفيش حاجة بتضمن إنها هتتنفذ مع بعض من غير مقاطعة.

فيه مثال حقيقي حصل في MySQL: متغير مشترك اسمه proc_info جوه struct اسمها thd. الـ thread الأول بيتأكد إن القيمة مش NULL، وبعدين يطبعها. المشكلة إن الـ thread التاني ممكن يحط القيمة NULL بالظبط في اللحظة اللي بين الفحص والطباعة. النتيجة: الـ thread الأول لما يوصل للطباعة، القيمة بقت NULL، فيحصل crash (null pointer dereference).

// Thread 1 بيفحص القيمة ويطبعها، Thread 2 بيمسحها في أي لحظة — من غير أي تنسيق بينهم
// Thread 1
if (thd->proc_info != NULL) {
    print_status(thd->proc_info);   // ممكن proc_info تبقى NULL هنا بالظبط
}

// Thread 2 (بيشتغل في نفس الوقت)
thd->proc_info = NULL;

الحل غالبًا بسيط: تحط lock حوالين أي استخدام للمتغير المشترك، عشان الفحص والاستخدام يحصلوا كوحدة واحدة متكاملة من غير ما thread تاني يقدر "يقفز" في النص.

// نفس الكود بعد الإصلاح — الفحص والاستخدام بقوا محميين بنفس الـ lock
pthread_mutex_t info_lock = PTHREAD_MUTEX_INITIALIZER;

// Thread 1
pthread_mutex_lock(&info_lock);
if (thd->proc_info != NULL) {
    print_status(thd->proc_info);
}
pthread_mutex_unlock(&info_lock);

// Thread 2
pthread_mutex_lock(&info_lock);
thd->proc_info = NULL;
pthread_mutex_unlock(&info_lock);

مهم: أي كود تاني بيلمس proc_info لازم يستخدم نفس الـ lock برضه، وإلا الحماية مش هتفيد حاجة.

Order Violation

التعريف الرسمي: بيحصل لما يكون فيه ترتيب متوقع بين عمليتين (المفروض A تحصل قبل B)، لكن الترتيب ده مش متضمن فعليًا وقت التشغيل — يعني B ممكن تحصل قبل A.

مثال شائع: thread رئيسي بيعمل create لـ thread تاني، والـ thread الجديد بيفترض إن متغير معين (زي pointer بتاع الـ thread نفسه) اتهيأ خلاص. المشكلة: لو الـ thread الجديد بدأ ينفذ فورًا، ممكن يوصل للمتغير ده قبل ما الـ thread الرئيسي يخلص تهيئته — فيحصل وصول لقيمة NULL أو غير مهيأة.

// Thread 2 بيفترض إن worker اتعمله init، بس مفيش أي ضمان لذلك
// Thread 1
void start_up() {
    worker = create_thread(worker_main, ...);
}

// Thread 2
void worker_main() {
    status = worker->state;   // ممكن worker لسه NULL هنا
}

الحل القياسي هو استخدام condition variable عشان تفرض الترتيب: الـ thread التاني ينتظر (wait) على إشارة (signal) من الأول، ومايكملش غير لما يتأكد إن التهيئة خلصت فعلًا.

// نفس الكود بعد إضافة condition variable لفرض الترتيب
pthread_mutex_t   lk   = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t    cv   = PTHREAD_COND_INITIALIZER;
int               ready = 0;

// Thread 1
void start_up() {
    worker = create_thread(worker_main, ...);
    pthread_mutex_lock(&lk);
    ready = 1;
    pthread_cond_signal(&cv);
    pthread_mutex_unlock(&lk);
}

// Thread 2
void worker_main() {
    pthread_mutex_lock(&lk);
    while (ready == 0)
        pthread_cond_wait(&cv, &lk);
    pthread_mutex_unlock(&lk);

    status = worker->state;   // دلوقتي مضمون إن worker اتهيأ
}

لو الـ Thread 2 بدأ الأول، هيقف مستني على الـ wait لحد ما يوصله الـ signal. ولو بدأ متأخر، هيلاقي ready خلاص = 1 فيكمل على طول من غير ما يستنى. الحالتين متغطيين.

ملحوظة مهمة

حسب دراسة Lu وزمايلها، ٩٧٪ من الـ non-deadlock bugs اللي درسوها كانت من النوعين دول بس (atomicity أو order). يعني لو انت كمبرمج بتركز على النمطين دول وانت بتراجع الكود، هتقدر تمسك أغلب المشاكل الشائعة. طبعًا مش كل الـ bugs سهلة زي المثالين دول — بعضها محتاج إعادة تصميم أعمق لبنية البيانات نفسها.

٢. Deadlock Bugs

المشكلة الكلاسيكية اللي بتظهر في الأنظمة اللي فيها locking protocols معقدة. بتحصل لما thread ماسك lock (خليها L1) وبينتظر lock تاني (L2)، وفي نفس الوقت الـ thread التاني ماسك L2 وبينتظر L1 يتفك. النتيجة: الاتنين واقفين لحد الأبد.

// كل thread بياخد اللوكات بترتيب عكسي عن التاني — احتمال deadlock حقيقي
// Thread 1              // Thread 2
pthread_mutex_lock(&L1);   pthread_mutex_lock(&L2);
pthread_mutex_lock(&L2);   pthread_mutex_lock(&L1);

الكود ده مش هيعمل deadlock دايمًا — بس فيه احتمال حقيقي: لو Thread 1 خد L1 وحصل context switch قبل ما ياخد L2، وThread 2 خد L2 وحاول ياخد L1... كل واحد فيهم دلوقتي مستني قفل ماسكه التاني. مفيش حد هيكمل.

الـ cycle في الرسمة (Thread 1 → L2 → Thread 2 → L1 → Thread 1) هو بالظبط علامة الـ deadlock.

ليه الـ Deadlocks بتحصل أصلًا؟

ممكن تفتكر إن حل زي "خلي الاتنين ياخدوا اللوكات بنفس الترتيب" هيحل المشكلة على طول — وده صح فعلاً في الأمثلة البسيطة. بس في الواقع، فيه سببين رئيسيين بيخلوا المشكلة دي مستمرة:

  1. تعقيد الـ dependencies في الأنظمة الكبيرة: خد مثلاً الـ operating system — الـ virtual memory subsystem ممكن يحتاج يوصل للـ file system عشان يجيب صفحة من الديسك، وفي نفس الوقت الـ file system ممكن يحتاج صفحة memory جديدة عشان يقرا فيها البيانات، فيحتاج يتواصل مع virtual memory subsystem. العلاقة الدائرية دي بين الأنظمة الفرعية بتخلي تصميم استراتيجية الـ locking حاجة محتاجة عناية شديدة.
  2. طبيعة الـ encapsulation: إحنا كمبرمجين متعلمين نخبي تفاصيل التنفيذ عشان الكود يبقى سهل البناء والتعديل (modularity). المشكلة إن المبدأ ده مش بيتماشى كويس مع الـ locking. مثال كلاسيكي: method في Java اسمها Vector.addAll(). لو عندك v1.addAll(v2)، الـ method دي محتاجة تاخد lock للـ vector الأساسي (v1) وللـ vector التاني (v2) عشان تضمن thread-safety. بتاخدهم بترتيب معين (مثلاً v1 الأول). لو thread تاني نادى في نفس اللحظة تقريبًا v2.addAll(v1)، بقى عندك احتمال deadlock حقيقي — وده كله متخبي جوه implementation الـ method، البرنامج اللي بيستخدمها مش شايف أي حاجة غلط في الكود بتاعه.

الشروط الأربعة اللازمة عشان يحصل Deadlock

لازم الأربع شروط دول كلهم يتحققوا مع بعض عشان يحصل deadlock. لو شرط واحد بس مش متحقق، الـ deadlock مستحيل يحصل — وده أساس كل استراتيجيات الحل اللي جاية.

١Mutual Exclusion

الـ threads بتاخد ownership حصري (exclusive) على المورد — زي ما بيحصل لما thread ياخد lock.

٢Hold-and-Wait

الـ thread فاضل ماسك موارد (locks) خدها فعلًا، وفي نفس الوقت بينتظر موارد إضافية (locks تانية).

٣No Preemption

مفيش حد يقدر ياخد lock بالقوة من thread ماسكه — لازم هو نفسه يسيبه.

٤Circular Wait

فيه سلسلة دائرية من الـ threads، كل واحد فيهم ماسك مورد الـ thread اللي جاي بعده في السلسلة بينتظره.

٣. Prevention — منع الـ Deadlock

بما إن الأربع شروط لازم يتحققوا كلهم مع بعض، فكل استراتيجية منع بتحاول تكسر شرط واحد بس من الأربعة عشان تضمن استحالة الـ deadlock.

كسر الـ Circular Wait

دي أعملي وأشيع تقنية بيستخدموها المبرمجين فعليًا. الفكرة: تفرض ترتيب ثابت (total ordering) لأخذ الـ locks. مثلاً لو عندك L1 وL2 بس في النظام كله، اجعل كل الكود من غير استثناء ياخد L1 قبل L2 دايمًا. الترتيب الصارم ده بيمنع أي cycle، وبالتالي مفيش deadlock.

في الأنظمة الكبيرة والمعقدة، عدد الـ locks بيبقى أكبر بكتير، فعمل total ordering يبقى صعب (وأحيانًا مش لازم أصلاً). الحل البديل: partial ordering — تحدد ترتيب معين بس بين مجموعات معينة من الـ locks بدل ما ترتبهم كلهم مع بعض. مثال حقيقي جدًا: كود memory-mapping في kernel لينكس فيه تعليق في أول الملف بيوضح حوالي عشر مجموعات مختلفة من ترتيب أخذ الـ locks، من مجموعات بسيطة لحد ترتيبات معقدة بتشمل أكتر من ٣-٤ locks مع بعض.

حيلة عملية: رتّب حسب عنوان الذاكرة

لو عندك function بتاخد اتنين lock كباراميترات، زي do_something(lock_t *a, lock_t *b)، المشكلة إن thread ممكن ينادي do_something(L1, L2) وthread تاني ينادي do_something(L2, L1) — فمهما كان الترتيب الداخلي جوه الـ function، دايمًا هيبقى فيه احتمال تعارض.

الحل الذكي: قارن عنوان الـ lock نفسه في الذاكرة (memory address)، وخد الأصغر عنوانًا أولاً دايمًا (أو الأكبر، المهم تكون ثابتة). كده مهما كان ترتيب الباراميترات اللي دخلت بيه، الترتيب الفعلي لأخذ الـ locks هيفضل ثابت.

كسر الـ Hold-and-Wait

الفكرة: تاخد كل الـ locks اللي محتاجها مرة واحدة، وبشكل atomic، من غير ما تسيب فرصة لأي context switch يحصل في النص. طريقة شائعة لتنفيذ ده: تستخدم "super lock" (خليها اسمها global_lock) تاخده الأول قبل أي محاولة لأخذ أي مجموعة locks.

// أخذ كل الـ locks المطلوبة تحت حماية super lock واحد يمنع أي تداخل
pthread_mutex_lock(&global_lock);   // بداية التجميع
pthread_mutex_lock(&L1);
pthread_mutex_lock(&L2);
// ... باقي الشغل
pthread_mutex_unlock(&global_lock); // النهاية

طالما كل thread بيلتزم إنه ياخد global_lock الأول قبل أي محاولة لأخذ locks تانية، حتى لو أخد بقية اللوكات بترتيب مختلف، مفيش مشكلة — لأنه أساسًا بيكون الوحيد الشغال في المنطقة دي.

المشكلة في الحل ده:

  • الـ encapsulation بتقف ضدك تاني هنا: عشان تنادي أي routine، لازم تعرف مقدمًا بالظبط أنهي locks هتتاخد جواها — وده مش دايمًا واضح.
  • بيقلل الـ concurrency، لأنك بتاخد كل اللوكات بدري (مرة واحدة) بدل ما تاخدها وقت ما تحتاجها فعليًا.

كسر الـ No-Preemption

أغلب مكتبات الـ threading بتوفر واجهة أكتر مرونة اسمها trylock: بدل ما تستخدم lock() العادية اللي بتوقف (block) الـ thread لحد ما تاخد الـ lock، trylock() بترجع فورًا — لو نجحت تاخد الـ lock بترجع نجاح، ولو الـ lock مشغول بترجع خطأ على طول من غير انتظار.

// لو فشلنا ناخد L2، نسيب L1 ونحاول من الأول — بدل ما نفضل مستنيين ونعمل deadlock
retry:
pthread_mutex_lock(&L1);
if (pthread_mutex_trylock(&L2) != 0) {
    pthread_mutex_unlock(&L1);
    goto retry;
}

بالطريقة دي، حتى لو thread تاني بياخد نفس اللوكات بترتيب معكوس (L2 قبل L1)، البرنامج مش هيعمل deadlock — لأن أي thread بيفشل في أخذ الـ lock التاني، بيسيب الأول ويحاول تاني بدل ما يفضل مستني لحد الأبد.

مشكلة جديدة: Livelock

ممكن (مع إنه مش شائع) اتنين threads يفضلوا يحاولوا وبيفشلوا مع بعض بنفس النمط، تكرارًا وبلا نهاية — مش deadlock (لأن الاتنين شغالين فعلًا)، بس مفيش تقدم حقيقي بيحصل. الحل الشائع: تضيف تأخير عشوائي (random delay) قبل ما تعيد المحاولة، عشان تقلل احتمال التصادم المتكرر بين نفس الـ threads.

الحل ده كمان له عيبين: الأول، لو الـ lock الأول متخبي جوه routine تانية (encapsulation تاني)، الرجوع للـ retry بيبقى أعقد في التنفيذ. والتاني: لو الكود خد موارد تانية غير اللوكات (زي allocate memory) في الطريق قبل ما يفشل، لازم يفكها كلها بعناية قبل ما يرجع يحاول من الأول تاني — وإلا هيحصل memory leak أو حاجة زيها.

ملحوظة أخيرة: الحل ده في الحقيقة مش بيضيف "preemption" فعلي (يعني مفيش حد بياخد الـ lock بالقوة من حد تاني) — هو بس بيدي الـ thread فرصة إنه "يسيب" ملكيته لنفسه بشكل لطيف (graceful) لو حس إنه هيتورط. برضه عمليًا الحل ده بيشتغل كويس جدًا.

إلغاء الـ Mutual Exclusion تمامًا

آخر استراتيجية، وهي الأصعب مفاهيميًا: بدل ما تحاول تدير الـ mutual exclusion بذكاء، تلغيها من أساسها. Herlihy كان أول من طرح فكرة إنك تبني data structures من غير أي locks خالص — الأسلوب ده معروف بـ lock-free (والمرتبط بيه wait-free)، باستخدام تعليمات هاردوير قوية زي compare-and-swap (CAS).

الـ CAS تعليمة atomic بيوفرها الهاردوير: بتاخد عنوان، وقيمة متوقعة، وقيمة جديدة. لو القيمة الحالية في العنوان بتطابق القيمة المتوقعة، بتغيرها للقيمة الجديدة وترجع نجاح؛ غير كده، ترجع فشل من غير ما تغير حاجة خالص — وكل ده بشكل atomic (خطوة واحدة مش قابلة للمقاطعة).

// compare-and-swap بشكل مبسط
int compare_and_swap(int *addr, int expected, int new_val) {
    if (*addr == expected) {
        *addr = new_val;
        return 1; // نجح
    }
    return 0; // فشل
}

مثال بسيط: تعمل increment لقيمة بشكل atomic من غير أي lock:

// نحاول نحدّث القيمة، ولو حد سبقنا وغيرها، نعيد المحاولة بالقيمة الجديدة
void atomic_add(int *value, int amount) {
    int old_val;
    do {
        old_val = *value;
    } while (compare_and_swap(value, old_val, old_val + amount) == 0);
}

بدل ما تاخد lock، تعمل التعديل، وبعدين تفك الـ lock — هنا بتحاول تحدّث القيمة باستمرار جوه loop، وتستخدم الـ CAS عشان تتأكد إن حد تاني ماغيرش القيمة من تحتك وانت شغال. مفيش lock خالص، وبالتالي مفيش deadlock ممكن يحصل (رغم إن livelock لسه احتمال وارد نظريًا).

مثال أعقد شوية: إضافة عنصر (node) في أول linked list (insert at head) بدون locks:

// لسه نجهز الـ node، ونحاول نخلي head يشاور عليه — ولو حد سبقنا غيّر head، نعيد المحاولة
void list_insert(int value) {
    node_t *n = malloc(sizeof(node_t));
    n->value = value;
    do {
        n->next = head;
    } while (compare_and_swap((int*)&head, (int)n->next, (int)n) == 0);
}

الفكرة: نخلي الـ node الجديد يشاور على head الحالي، وبعدين نحاول بـ CAS نخلي head يشاور على node الجديد. لو thread تاني كان أسرع وغيّر head من تحتنا، محاولتنا هتفشل، فنعيدها تاني بالقيمة الجديدة لـ head — وهكذا لحد ما تنجح.

طبعًا بناء list كامل تقدر تعمله insert وdelete وlookup بشكل lock-free بالكامل حاجة أعقد بكتير من مجرد insert بسيط — ده مجال بحثي قائم بذاته (lock-free / wait-free data structures)، وصعوبته من أسباب إن استخدامه محدود في الواقع رغم فايدته النظرية.

٤. Avoidance — تجنب الـ Deadlock عن طريق الـ Scheduling

بدل ما "تمنع" الـ deadlock بتغيير طريقة كتابة الكود، فيه أسلوب بديل: تتجنبه عن طريق الـ scheduling الذكي. الفكرة تتطلب معرفة شاملة (global knowledge) مقدمًا بكل الـ locks اللي كل thread هياخدها خلال تنفيذه، وبعدين تجدول الـ threads بطريقة تضمن إن الـ deadlock مستحيل يحصل.

مثال ١ — تعارض جزئي

افترض عندك ٢ processors و٤ threads. T1 وT2 كل واحد بياخد L1 وL2. T3 باخد L2 بس. T4 مابياخدش أي lock:

T1T2T3T4
L1yesyesnono
L2yesyesyesno

الـ scheduler الذكي هنا يقدر يستنتج إنه طالما T1 وT2 محصلش يشتغلوا في نفس اللحظة، مفيش أي احتمال deadlock — سواء T3 اشتغل مع T1 أو مع T2 أو حتى مع T4 مش هيسبب مشكلة، لأن T3 بياخد lock واحد بس أصلًا.

زي ما واضح، الـ static scheduling هنا محافظ (conservative) جدًا — T1 وT2 وT3 اتحطوا كلهم على نفس البروسيسور، فالوقت الإجمالي لإنهاء الشغل بيطول بشكل واضح. كان ممكن نظريًا نشغلهم بالتوازي، بس الخوف من الـ deadlock بيمنعنا، والتضحية هنا في الأداء (performance).

مش كل حاجة لازم تتعمل بالكمال (Tom West's Law)

مقولة مشهورة في هندسة الأنظمة: "مش كل حاجة تستاهل تتعمل تستاهل كمان تتعمل ١٠٠٪ صح". لو مشكلة معينة نادرة الحدوث وتكلفتها لو حصلت بسيطة، مفيش داعي تصرف مجهود ضخم عشان تمنعها بالكامل. لكن لو كنت بتبني نظام حرج (زي مركبة فضائية!) وتكلفة الخطأ كارثية، وقتها الحكاية تختلف تمامًا.

أشهر خوارزمية في المجال ده هي Banker's Algorithm بتاعة Dijkstra. المشكلة إن الأسلوب ده مفيد بس في بيئات محدودة جدًا — زي embedded systems لما يكون عندك معرفة كاملة مقدمًا بكل الـ tasks والـ locks اللي هيحتاجوها. وزي ما شفنا في المثال التاني، الأسلوب ده بيقلل الـ concurrency بشكل واضح. عشان كده، الـ avoidance عن طريق الـ scheduling مش حل عام مستخدم على نطاق واسع في الواقع.

٥. Detect and Recover — اكتشاف وعلاج الـ Deadlock

الاستراتيجية الأخيرة والأكتر واقعية في كتير من الأنظمة: تسيب الـ deadlock يحصل من وقت للتاني (نادرًا)، وتاخد إجراء بعد ما تكتشفه، بدل ما تحاول تمنعه أو تتجنبه بالكامل من البداية.

فكر في الموضوع كده: لو نظام تشغيل بيهنج مرة كل سنة، غالبًا هتعمل restart وتكمل شغلك عادي. لو الـ deadlocks نادرة فعلًا، الحل "الكسول" ده يبقى عملي جدًا في الواقع.

كتير من أنظمة الـ databases بتستخدم بالفعل تقنيات deadlock detection and recovery: فيه "deadlock detector" بيشتغل بشكل دوري، بيبني resource graph (شبيه بالرسمة اللي شفناها فوق) ويفحص وجود cycles فيه. لو لقى cycle، معناها فيه deadlock فعلي، والنظام محتاج يتخذ إجراء — زي إعادة تشغيل بعض العمليات المتورطة. لو الإصلاح محتاج دقة أكبر في بنية البيانات، ممكن يستدعي الأمر تدخل بشري لإصلاح الحالة يدويًا.

الخلاصة

الشابتر غطى نوعين من الـ concurrency bugs:

  • Non-deadlock bugs: شائعة جدًا في الواقع (بالنسبة تفوق الديدلوك)، لكنها غالبًا أسهل في الإصلاح. بتنقسم لـ atomicity violations (سلسلة تعليمات المفروض تتنفذ مع بعض ما اتنفذتش) وorder violations (ترتيب مطلوب بين عمليتين ماتفرضش وقت التشغيل).
  • Deadlock: مشكلة قديمة قد الـ concurrency نفسها، اتكتب فيها مئات الأبحاث. أفضل حل عملي في الواقع هو الحرص والانضباط: تفرض ترتيب واضح لأخذ اللوكات من البداية (lock ordering)، وده بيمنع المشكلة من أساسها في أغلب الحالات.

الأساليب اللي بتلغي الحاجة للـ locks خالص (lock-free / wait-free) واعدة، وبدأت فعلًا تدخل مكتبات مستخدمة على نطاق واسع (زي بعض أجزاء لينكس)، بس تعقيد بنائها بيحد من انتشارها العام. في الآخر، ممكن يكون أفضل حل بعيد المدى هو تصميم نماذج برمجة متوازية جديدة أصلًا مالهاش علاقة باللوكات — زي MapReduce من Google، اللي بتخلي المبرمج يوصف حسابات متوازية معينة من غير ما يحتاج يلمس lock واحد طول الوقت. الـ locks بطبيعتها فيها مشاكل — يمكن أحسن استراتيجية إننا نتجنب استخدامها أصلًا إلا لو محتاجينها فعلًا.
