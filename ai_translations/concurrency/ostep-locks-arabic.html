1. إيه المشكلة أصلاً؟ 🤔

احنا عارفين من موضوع الـ concurrency إن فيه مشكلة أساسية: عايزين ننفذ مجموعة تعليمات كأنها عملية واحدة (atomic)، بس بسبب الـ interrupts على البروسيسور الواحد، أو وجود أكتر من thread شغالة على أكتر من processor في نفس الوقت، مش هنقدر نضمن كده ببساطة. الجزء ده من الكود اللي محتاج يتنفذ من غير مقاطعة اسمه critical section.

الحل اللي هنتكلم عنه هنا هو الـ Lock. إحنا كمبرمجين بنحط لوك حوالين أي critical section عشان نضمن إنها تتنفذ وكأنها تعليمة واحدة atomic، حتى لو فعليًا هي كذا سطر كود.

2. فكرة الـ Lock الأساسية 🔑

مثال بسيط: لو عندك عملية زي تحديث رصيد مشترك بين threads كتير:

balance = balance + 1;

عشان نحميها بلوك، بنكتب:

lock_t mutex;   // متغير اللوك، معرّف global

lock(&mutex);
balance = balance + 1;
unlock(&mutex);

الـ lock نفسه مجرد متغير، وبيكون في حالة من اتنين: available / free يعني مفيش thread ماسكه، أو acquired / held يعني في thread واحد بالظبط ماسكه ودخل الـ critical section.

ازاي بيشتغل؟
1
Thread بينادي lock(). لو اللوك فاضي، بياخده ويدخل الـ critical section (بقى "المالك" owner).
2
لو thread تاني نادى lock() في نفس الوقت، مش هيرجعله الفنكشن لحد ما اللي ماسك اللوك يسيبه.
3
لما المالك ينادي unlock()، اللوك يبقى فاضي تاني، ولو فيه threads تانية مستنية، واحد منهم هياخده.

اللوكس بتديلك تحكم بسيط في الـ scheduling: الـ OS بيشغّل الـ threads إزاي ما يحب، بس اللوك بيضمنلك إن كود معين مايشتغلش غير بـ thread واحد في المرة الواحدة، وده بيحول الفوضى بتاعة الـ scheduling لحاجة متحكم فيها أكتر.

3. Pthread Mutex 📚

في POSIX (المكتبة القياسية للـ threads في لينكس)، اسم الـ lock هو mutex، اختصار لـ "mutual exclusion"، لأنه بيمنع أكتر من thread من الدخول للـ critical section في نفس الوقت. 

pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

pthread_mutex_lock(&lock);
balance = balance + 1;
pthread_mutex_unlock(&lock);

لاحظ إن كل مرة بتمرر مؤشر للـ lock نفسه، لإنك ممكن تستخدم أكتر من mutex مختلف عشان تحمي بيانات مختلفة. ده بيدّيك مرونة:

الاستراتيجيةالوصف
Coarse-grainedلوك واحد كبير بيحمي كل حاجة — بسيط بس بيقلل التوازي
Fine-grainedكل بنية بيانات ليها لوك خاص بيها — أعقد شوية بس بيسمح بـ threads أكتر تشتغل مع بعض

4. إزاي نقيّم أي Lock؟ ⚖️

السؤال الأساسي: إزاي نبني لوك كفء؟ محتاجين نعرف نقيّمه على إيه.
  • Correctness (الصحة): هل فعلاً بيمنع أكتر من thread يدخل الـ critical section في نفس الوقت؟
  • Fairness (العدالة): هل كل thread مستني اللوك هياخد فرصته؟ ولا ممكن يفضل مستني للأبد (starvation)؟
  • Performance (الأداء): إيه تكلفة استخدام اللوك في الحالات دي:
    • لما مفيش تنافس (thread واحد بس بياخد ويسيب اللوك)
    • لما فيه أكتر من thread بيتنافسوا على نفس البروسيسور
    • لما فيه threads على أكتر من CPU بيتنافسوا مع بعض

5. الحل القديم: تقفيل الـ Interrupts 🚫

من أقدم الحلول (للأنظمة اللي فيها processor واحد بس): تقفل الـ interrupts قبل ما تدخل الـ critical section، وتفتحها تاني بعد ما تخرج.

void lock()   { disable_interrupts(); }
void unlock() { enable_interrupts();  }

الميزة: بسيط جدًا — طالما مفيش مقاطعة، مفيش thread تاني هيقاطعك.

المشاكل:
  • لازم تثق في أي thread بينادي اللوك إنه مش هيسيء استخدام الصلاحية دي (ممكن برنامج شرير أو فيه خطأ يقفل الـ interrupts ويدخل في loop لا نهائي — والحل الوحيد وقتها إعادة تشغيل الجهاز).
  • مش شغال أصلاً على أنظمة فيها أكتر من processor: تقفيل الـ interrupts بيأثر على processor واحد بس، والـ threads التانية هتفضل شغالة على الـ processors التانية وتدخل الـ critical section عادي.
  • لو قفلت الـ interrupts فترة طويلة، ممكن تضيع interrupts مهمة (زي إشعار إن قرص انتهى من عملية قراءة).

لكل الأسباب دي، الطريقة دي بقت مستخدمة بس جوه الـ OS نفسه في حالات محدودة (لإن الـ OS بيثق في نفسه أصلاً).

6. محاولة فاشلة: بس متغير عادي 😬

خلينا نجرب نبني لوك باستخدام متغير flag عادي، من غير أي دعم من الـ hardware:

typedef struct { int flag; } lock_t;

void init(lock_t *m) { m->flag = 0; }

void lock(lock_t *m) {
    while (m->flag == 1)   // اختبار القيمة
        ;                  // فضل مستني (spin)
    m->flag = 1;           // هنا حط القيمة
}

void unlock(lock_t *m) { m->flag = 0; }

الفكرة تبان سليمة، بس فيها مشكلة خطيرة: العملية while + set مش atomic! تخيل السيناريو ده:

Thread 1: بيدخل lock()، بيشوف flag == 0، وقبل ما يحط flag = 1 بتاعته، بتحصل interrupt وينده على Thread 2.
Thread 2: بيدخل lock() برضه، بيشوف flag لسه == 0 (لإن Thread 1 لسه مغيرهاش)، فيحط flag = 1 ويدخل الـ critical section.
بعدين يرجع الدور لـ Thread 1، وهو كمان يحط flag = 1 ويدخل الـ critical section.
النتيجة: الاتنين Threads دخلوا الـ critical section في نفس الوقت! دي كارثة (violation للـ mutual exclusion).

كمان فيه مشكلة أداء: الطريقة اللي بتستخدم فيها الـ thread المستنية اللوك اسمها spin-waiting — بتفضل تلف في الـ loop وتستهلك وقت الـ CPU من غير فايدة، وده مؤلم جدًا خصوصًا لو فيه processor واحد بس (لإن الـ thread اللي ماسكة اللوك مش هتقدر تشتغل أصلاً وقت ما التانية بتلف فاضي).

7. الحل: Test-And-Set 🛠️

عشان نحل المشكلة، محتاجين تعليمة من الـ hardware نفسه بتعمل "اختبار + تحديث" في خطوة واحدة atomic، اسمها test-and-set (على x86 اسمها xchg، وعلى SPARC اسمها ldstub). 

// كل ده بيحصل atomically في تعليمة واحدة من الـ hardware
int test_and_set(int *ptr, int new_val) {
    int old_val = *ptr;
    *ptr = new_val;
    return old_val;
}

بنستخدمها كده لبناء spin lock صحيح:

typedef struct { int flag; } lock_t;

void init(lock_t *m) { m->flag = 0; }

void lock(lock_t *m) {
    while (test_and_set(&m->flag, 1) == 1)
        ;   // فاضل مستني لحد ما ترجع 0
}

void unlock(lock_t *m) { m->flag = 0; }
ليه ده شغال؟ لأن العملية "اقرا القديمة واكتب الجديدة" بتحصل في خطوة واحدة مايقدرش أي thread تاني يتدخل فيها. لو اللوك فاضي (flag=0)، أول thread بينادي test_and_set هيلاقي القيمة القديمة 0، فمعناها هو نجح ياخد اللوك، وفي نفس اللحظة بقت 1. أي thread تاني بعد كده هيلاقي القيمة اللي بترجعله دايمًا 1 لحد ما اللي ماسك اللوك يسيبه.

النوع ده من اللوكس اسمه spin lock — أبسط نوع لوك ممكن تبنيه، وبيحتاج scheduler بيعمل preemption (يقاطع الـ threads بالتايمر) عشان يشتغل صح على processor واحد.

تقييم الـ Spin Lock

المعيارالتقييم
Correctness✅ تمام — بيضمن mutual exclusion فعلاً
Fairness❌ مفيش أي ضمان — ممكن thread تفضل مستنية للأبد (starvation)
Performance (processor واحد)❌ ممكن يكون مكلف جدًا لو الـ thread الماسكة اللوك اتقاطعت جوه الـ critical section
Performance (أكتر من CPU)✅ كويس نسبيًا لو عدد الـ threads قريب من عدد الـ CPUs، لإن الـ critical section عادةً قصيرة

8. Compare-And-Swap 🔄

تعليمة hardware تانية، بتقارن القيمة الحالية بقيمة متوقعة، ولو اتطابقوا تحدّثها:

int compare_and_swap(int *ptr, int expected, int new_val) {
    int original = *ptr;
    if (original == expected)
        *ptr = new_val;
    return original;
}

بنستخدمها بنفس فكرة test-and-set:

void lock(lock_t *m) {
    while (compare_and_swap(&m->flag, 0, 1) == 1)
        ;   // spin
}

الفرق إنها أقوى من test-and-set، وبتتستخدم في تقنيات lock-free أكتر تعقيدًا.

9. Load-Linked / Store-Conditional 🔗

بعض المعماريات (MIPS, ARM, PowerPC, Alpha) بتوفر زوج تعليمات بيشتغلوا مع بعض:

  • load_linked: زي أي عملية قراءة عادية.
  • store_conditional: بتنجح وتحدّث القيمة بس لو مفيش حد كتب على نفس العنوان من وقت الـ load_linked. لو حصل تعارض، بترجع فشل (0).
void lock(lock_t *m) {
    while (1) {
        while (load_linked(&m->flag) == 1)
            ;   // استنى لحد ما تبقى صفر
        if (store_conditional(&m->flag, 1) == 1)
            return;   // نجحنا، خدنا اللوك
        // لو فشلنا، نرجع نجرب تاني
    }
}

10. Fetch-And-Add و Ticket Locks 🎟️

تعليمة بتزود قيمة وترجع القيمة القديمة، في خطوة واحدة atomic:

int fetch_and_add(int *ptr) {
    int old_val = *ptr;
    *ptr = old_val + 1;
    return old_val;
}

باستخدامها، بنقدر نبني Ticket Lock اللي بيحل مشكلة الـ fairness! الفكرة زي تذاكر الدور في البنك: كل thread بياخد رقم تذكرة (ticket)، وفيه متغير turn بيحدد دور مين دلوقتي. 

typedef struct { int ticket; int turn; } lock_t;

void init(lock_t *m) { m->ticket = 0; m->turn = 0; }

void lock(lock_t *m) {
    int my_turn = fetch_and_add(&m->ticket);
    while (m->turn != my_turn)
        ;   // استنى دورك
}

void unlock(lock_t *m) { m->turn = m->turn + 1; }
الفرق المهم: Ticket lock بيضمن إن كل thread هيدخل الـ critical section في يوم من الأيام، لإن كل واحد ليه رقم دور محدد. عكس test-and-set اللي ممكن thread تفضل تلف لحد ما تجيب حظها.

11. مشكلة الـ Spinning الكتير 😩

المشكلة: تخيل thread ماسكة اللوك وبعدين اتقاطعت (context switch) قبل ما تسيبه. أي thread تانية هتحاول تاخد اللوك هتلاقيه ماسوك، فتفضل تلف (spin) طول الـ time slice بتاعتها من غير فايدة. لو فيه N threads بتتنافس، ممكن نضيع N-1 time slice بالبلاش.

الحلول اللي هيقدمها الـ hardware لوحده مش كفاية — لازم دعم من الـ OS كمان.

الحل الأول: Yield بس

void lock(lock_t *m) {
    while (test_and_set(&m->flag, 1) == 1)
        yield();   // سيب المعالج لـ thread تانية
}

أحسن من الـ spinning العادي، بس لسه فيه تكلفة (context switch مش رخيص)، ولسه ممكن يحصل starvation.

12. الحل الحقيقي: نوّم بدل ما تلف 😴

الحل الأدق: استخدام queue عشان نتحكم مين اللي هياخد اللوك بعد كده، مع دعم من الـ OS زي:

  • park(): بينوّم الـ thread الحالية.
  • unpark(thread_id): بيصحّي thread معينة.

الفكرة العامة (زي ما اتعملت في Solaris مثلًا):

1
لما thread تحاول تاخد لوك ماسوك، بتحط نفسها في queue الانتظار وتنده على park() تنام.
2
لما الـ thread الماسكة اللوك تخلص وتنده على unlock()، لو فيه حد في الـ queue، بتنده unpark() عليه يصحّى ويدخل الـ critical section مباشرة (من غير ما اللوك يترجع "فاضي" في نص الطريق).

Linux: Futex

لينكس بتستخدم آلية اسمها futex، فيها integer واحد بيخزن حالتين: البت الأعلى بيقول اللوك ماسوك ولا لأ، والباقي بيعد عدد الـ threads المستنية. الميزة إنها سريعة جدًا في الحالة الشائعة (مفيش تنافس)، وبتستخدم futex_wait و futex_wake للتعامل مع الـ queue جوه الـ kernel.

Two-Phase Locks

فكرة هجينة: أول حاجة الـ thread تعمل spin شوية (مرحلة أولى)، على أمل إن اللوك هيتفك قريب. لو ماحصلش، تدخل مرحلة تانية وتنام (park) لحد ما توصلها إشارة إن اللوك بقى فاضي. الفكرة إنك بتستفيد من مميزات الطريقتين: سرعة الـ spinning لو اللوك هيتفك بسرعة، وتوفير الـ CPU لو مش هيتفك قريب.

13. تنبيه مهم: Priority Inversion ⚠️

مشكلة تانية بتحصل خصوصًا مع الـ spin locks: تخيل thread عندها priority عالي (T2) وthread تانية priority واطي (T1). لو T1 خدت اللوك، وبعدين T2 (الأعلى أولوية) حاولت تاخده، هتفضل تلف (spin) لحد ما T1 تشتغل تاني وتسيب اللوك — بس لو الـ scheduler دايمًا بيفضّل T2 على T1، ممكن T1 محتاجش تشتغل تاني، فالنظام يقف تمامًا!

حتى من غير spin locks، المشكلة ممكن تحصل بشكل أعقد لو فيه 3 threads بأولويات مختلفة — الظاهرة دي معروفة وحصلت فعلًا في مهمة "مارس باثفايندر" الفضائية الشهيرة!

الحلول: تجنب استخدام spin locks في المواقف دي، أو استخدام تقنية اسمها priority inheritance (الـ thread صاحبة الأولوية الأعلى بتدي مؤقتًا أولويتها للـ thread الماسكة اللوك عشان تخلص بسرعة).

14. الخلاصة 📝

اللوكس الحقيقية بتتبني من مزيج بين:

  • 🔧 دعم من الـ hardware: تعليمات atomic زي test-and-set، compare-and-swap، load-linked/store-conditional، fetch-and-add.
  • 🖥️ دعم من الـ OS: زي park()/unpark() في Solaris، أو futex في لينكس، عشان الـ threads تنام بدل ما تضيّع وقت CPU وهي بتلف فاضي.

كل تقنية ليها مقايضة (trade-off) بين البساطة، الـ fairness، والأداء تحت ظروف مختلفة (processor واحد vs أكتر، تنافس قليل vs كتير). مفيش حل واحد "الأفضل مطلقًا" — الاختيار بيعتمد على الـ workload والـ hardware اللي شغال عليه.
