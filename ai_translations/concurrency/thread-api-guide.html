واجهة الـ Thread API

شرح مبسط بالعربي المصري لأهم دوال الـ POSIX threads: الإنشاء، الانتظار، الأقفال، وMonitor variables.

ملحوظة: ده مش ترجمة حرفية للفصل من الكتاب — ده شرح وتلخيص بأسلوبي للأفكار والدوال الأساسية اللي جايه في الفصل، عشان أحافظ على حقوق النشر بتاعة الكتاب الأصلي. لو عايز تقرأ النص الأصلي كامل، هو متاح مجانًا من نفس اللينك اللي بعتهولي.
THE CRUX

السؤال اللي الفصل ده بيجاوب عليه: إيه الـ interface اللي المفروض الـ OS يقدمه عشان تقدر تعمل threads وتتحكم فيهم، وإزاي التصميم ده يبقى سهل الاستخدام ومفيد في نفس الوقت؟

27.1

● إنشاء الـ Threads

أول حاجة محتاجها عشان تكتب برنامج multi-threaded هي إنك تعرف تعمل thread جديد. في POSIX الموضوع بسيط، فيه دالة واحدة اسمها pthread_create:

#include <pthread.h>

int pthread_create(
    pthread_t          *thread,
    const pthread_attr_t *attr,
    void            *(*start_routine)(void*),
    void            *arg
);

الدالة دي بتاخد 4 حاجات:

thread pointer لـ struct نوعها pthread_t. ده الـ "مقبض" (handle) اللي هتستخدمه بعد كده عشان تتعامل مع الـ thread ده — مثلًا تستناه لما يخلص.
attr إعدادات اختيارية للـ thread (زي حجم الـ stack أو أولوية الـ scheduling). في 99% من الحالات مبتحتاجهاش، فبتبعت NULL وخلاص.
start_routine ده function pointer — يعني اسم الدالة اللي الـ thread الجديد هيبدأ ينفذها. لازم تاخد void* وترجع void*.
arg القيمة اللي هتتبعت لـ start_routine لما الـ thread يبدأ شغل. عشان كده نوعها void* — تقدر تبعت أي نوع بيانات عايزه.

ليه void* بالذات؟ عشان تقدر تبعت أي نوع arguments، وترجع أي نوع نتيجة، من غير ما الدالة تكون مقيدة بنوع بيانات معين.

مثال

لو عايز تبعت أكتر من قيمة، بتلمهم في struct واحدة وتبعت pointer ليها:

typedef struct {
    int num1;
    int num2;
} task_args_t;

void *worker(void *arg) {
    task_args_t *a = (task_args_t *) arg;
    printf("%d %d\n", a->num1, a->num2);
    return NULL;
}

int main() {
    pthread_t t;
    task_args_t args = { 10, 20 };

    pthread_create(&t, NULL, worker, &args);
    // ...
}

بمجرد ما بتنادي pthread_create، بقى عندك entity تانية شغالة فعليًا — ليها الـ call stack بتاعها، بس بتشارك نفس الـ address space مع باقي الـ threads في البرنامج.

27.2

● استنى الـ Thread يخلص

لو عايز تستنى thread لحد ما يخلص شغله، تستخدم pthread_join:

int pthread_join(pthread_t thread, void **value_ptr);
الباراميتروظيفته
threadالـ handle بتاع الـ thread اللي عايز تستناه (نفس الـ variable اللي عبيتها في pthread_create)
value_ptrpointer للمكان اللي عايز ترجع فيه القيمة اللي الـ thread رجعها. لاحظ إنه void** مش void*، لأن الدالة نفسها بتغيّر القيمة دي.

لو مش محتاج القيمة الراجعة، تقدر تبعت NULL بسيطة. ولو الـ thread مش محتاج arguments أصلًا، تقدر تبعت NULL في pthread_create برضو.

⚠ تحذير مهم جدًا

مينفعش أبدًا ترجع pointer لـ variable متعمل allocate ليها على الـ stack بتاع الـ thread. لما الـ thread يخلص وينرجع، الـ stack بتاعه بيتمسح تلقائي — فأي pointer راجع بيبقى بيشاور على memory اتفرغت، وده بيسبب undefined behavior (bug صعب جدًا تلاقيه).

// غلط — الـ struct دي على الـ stack، هتتمسح لما الدالة ترجع
void *worker(void *arg) {
    result_t bad_result;   // ALLOCATED ON STACK!
    bad_result.x = 1;
    return (void *) &bad_result;   // خطر!
}

الحل: استخدم malloc عشان القيمة تتحط على الـ heap، وسيبها موجودة لحد ما المستدعي (caller) يستخدمها ويعمل free بعدين.

💡 مش كل برنامج multi-threaded محتاج pthread_join. مثلًا web server بيعمل worker threads بتفضل شغالة على طول عشان تستقبل requests — مفيش داعي تستناها. لكن أي برنامج parallel بيوزع شغل على threads وعايز يتأكد إن الكل خلص قبل ما يكمل، هيحتاج join.
27.3

● الأقفال — Locks

بعد الإنشاء والانتظار، أهم حاجة في مكتبة pthreads هي الأقفال، اللي بتضمنلك mutual exclusion (يعني thread واحد بس يدخل الـ critical section في نفس الوقت):

int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_unlock(pthread_mutex_t *mutex);

الفكرة: لو الـ lock فاضي، الـ thread بياخده ويدخل الـ critical section. لو محجوز، الـ thread بيستنى (blocked) لحد ما اللي حاجزه يعمل unlock.

pthread_mutex_t lock;

pthread_mutex_lock(&lock);
counter = counter + 1;   // critical section
pthread_mutex_unlock(&lock);

لازم تعمل init الأول

الكود اللي فوق ده ناقصه حاجة مهمة: الـ lock لازم يتعمله init قبل ما تستخدمه. فيه طريقتين:

ثابتة (static)ديناميكية (runtime)
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER; pthread_mutex_init(&lock, NULL);

الطريقة الديناميكية هي الأكتر استخدامًا، وبعد ما تخلص من الـ lock لازم تعمل pthread_mutex_destroy.

⚠ افحص return codes

زي أي دالة في UNIX، lock وunlock ممكن يفشلوا. لو ماتفحصش الـ return code، الفشل هيحصل بصمت — وده ممكن يخلي أكتر من thread يدخلوا الـ critical section في نفس الوقت من غير ما تحس!

دوال تانية للأقفال

int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_timedlock(pthread_mutex_t *mutex,
                             struct timespec *abs_timeout);

trylock بيرجع فشل فورًا لو الـ lock محجوز (مش بيستنى). timedlock بيستنى لحد وقت معين وبعدين يبطل. الاستخدام الشائع لهم هو الحالات اللي عايز تتجنب فيها إنك تتعلق (stuck) للأبد في انتظار قفل — زي مواضيع الـ deadlock اللي هنشوفها بعدين.

27.4

● Condition Variables

لو thread محتاج يستنى thread تاني "يعمل حاجة" الأول، هنا بييجي دور الـ condition variables. الدالتين الأساسيتين:

int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);
int pthread_cond_signal(pthread_cond_t *cond);

لازم كل condition variable يبقى ليها lock مرتبط بيها، ولازم الـ lock ده يكون محجوز وقت ما بتنادي أي من الدالتين.

Thread المستني

pthread_mutex_lock(&lock);
while (ready == 0)
    pthread_cond_wait(&cond, &lock);
pthread_mutex_unlock(&lock);

Thread اللي بيصحّي التاني

pthread_mutex_lock(&lock);
ready = 1;
pthread_cond_signal(&cond);
pthread_mutex_unlock(&lock);
ليه wait بتاخد lock وsignal لأ؟ لأن pthread_cond_wait بتعمل حاجتين: تنوّم الـ thread، وتفك الـ lock في نفس اللحظة (عشان الـ thread التاني يقدر ياخد الـ lock ويعمل signal). ولما الـ thread يصحى، الدالة بترجع تاخد الـ lock تاني قبل ما ترجع.
ليه while مش if؟ لأن فيه implementations ممكن "توقّظ" الـ thread غلط (spurious wakeup) من غير إن الشرط اتغير فعلًا. فلازم تتأكد من الشرط تاني بعد ما تصحى — الصحيان نفسه مجرد "تلميح" مش حقيقة مؤكدة.
⚠ ماتستخدمش flag عادي بدل condition variable

ممكن تتوسوس تستخدم while (ready == 0) ; (spinning) بدل condition variable. متعملش كده أبدًا: أولًا بتضيع CPU cycles وانت مستني، وثانيًا الـ ad-hoc synchronization ده بيبقى مليان bugs — أبحاث فعلية لقت إن حوالي نص الاستخدامات بتاعته فيها bugs.

27.5

● الكومبايل والتشغيل

لازم تعمل include لـ pthread.h، وعند الـ linking لازم تضيف flag اسمها -pthread:

$ gcc -o main main.c -Wall -pthread
27.6

● نصائح ختامية

دول أهم النصايح اللي المفروض تفتكرها وانت شغال بـ pthreads (أو أي thread library تانية):

01
خليك بسيط. أي كود بيعمل lock أو signal بين threads لازم يكون أبسط ما يمكن — الـ interactions المعقدة بتجيب bugs.
02
قلّل التفاعل بين الـ threads. كل ما التفاعلات تقل وتبقى مدروسة، كل ما أحسن.
03
اعمل init للأقفال والـ condition variables. نسيان ده بيدي كود بيشتغل أحيانًا ويفشل أحيانًا بطرق غريبة.
04
افحص الـ return codes دايمًا. إهمال ده بيدي behavior غريب وصعب تفهمه.
05
خد بالك من تمرير الـ arguments والقيم الراجعة. لو بتبعت reference لحاجة على الـ stack، غالبًا انت غلطان.
06
كل thread ليه stack خاص بيه. أي variable محلية جوه دالة الـ thread بتبقى خاصة بيه؛ لو عايز تشارك بيانات بين threads، لازم تكون على الـ heap.
07
استخدم condition variables دايمًا للتواصل بين threads. مش flags عادية.
08
اقرا الـ man pages. خصوصًا على Linux، فيها تفاصيل كتير مفيدة.
💡 الجزء الصعب في الـ threads مش الـ API نفسه — دي دوال بسيطة نسبيًا. الصعوبة الحقيقية في المنطق (logic) بتاع إزاي تبني برنامج concurrent صح.
