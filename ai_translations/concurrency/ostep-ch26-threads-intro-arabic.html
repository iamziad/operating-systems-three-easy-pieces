مقدمة في الـ Concurrency

threads-intro.pdf — Concurrency: An Introduction

إحنا فاهمين دلوقتي إزاي الـ OS واخد CPU واحد فيزيائي وحوّله لوهم إننا شغالين على كذا CPU (processes)، وإزاي واخد الـ RAM وحوّلها لوهم إن كل process عندها address space خاص بيها لوحدها. دلوقتي هنفتح باب جديد كل شيء: مش هنتكلم عن processes منفصلة، هنتكلم عن إننا نحط أكتر من نقطة تنفيذ (execution) جوه الـ process الواحدة نفسها. اسم الحكاية دي: thread.

* 1. الـ Thread ده إيه بالظبط؟

الصورة الكلاسيكية للـ process إن عندها نقطة تنفيذ واحدة بس: program counter (PC) واحد بيتحرك من instruction للتانية. الـ multi-threaded process كسرت الصورة دي: بقى عندك أكتر من PC شغال في نفس الوقت جوه نفس الـ process. كل thread من دول شبه process صغيرة بجواها، بس فيه فرق جوهري واحد: كل الـ threads بتشارك نفس الـ address space، يعني بتقدر توصل لنفس الـ data من غير ما تحتاج IPC أو shared memory segment زي ما بيحصل بين processes منفصلة.

يعني state الـ thread فيها حاجات شبه الـ process: PC بتاعها، registers خاصة بيها. لو عندك T1 و T2 شغالين على نفس الـ core، وقت ما الـ scheduler يقرر ينقل من T1 لـ T2، لازم يحصل context switch: يحفظ registers الـ T1 (بما فيها الـ PC) في مكان اسمه TCB (Thread Control Block) — نفس فكرة الـ PCB بتاع الـ process، بس هنا لكل thread. الفرق الكبير هنا: الـ address space فاضل زي ما هو، يعني مفيش تبديل page table زي ما بيحصل بين processes — وده اللي بيخلي التبديل بين threads أرخص عادةً من التبديل بين processes كاملة.

** كل Thread عنده Stack خاص بيه

في الـ process العادية (single-threaded)، شكل الـ address space معروف: الـ code تحت، فوقه الـ heap بيكبر لفوق، وفي أعلى الـ address space الـ stack بيكبر لتحت، وفي النص مساحة فاضية. المشكلة إن الـ stack هو اللي بيحمل local variables والـ return addresses وparameters بتاعت الدوال — ولو عندك أكتر من thread، كل واحد فيهم لازم يكون له stack خاص بيه (وإلا هيضربوا بعض).

Single-threaded
Stack ↓
Multi-threaded (2 threads)
Stack (T1) ↓
Stack (T2) ↓

أي متغير محلي أو return value بيتخزن في الـ stack بتاع نفس الـ thread، وده بيتسمى أحياناً thread-local storage. المشكلة الجانبية: الـ address space الجميلة اللي كانت مقسومة نضيف (heap وstack بيكبروا من طرفين مختلفين) بقت مزدحمة شوية دلوقتي إن فيه أكتر من stack. عادةً مش مشكلة كبيرة، لأن الـ stacks مش بتكبر جداً غير في حالة recursion تقيلة.

* 2. طيب ليه أصلاً نستخدم Threads؟

فيه سببين رئيسيين:

1 — Parallelism

لو عندك شغل زي جمع arrays كبيرة أو زيادة كل عنصر فيها برقم معين، وعندك أكتر من core فعلياً، تقدر تقسّم الشغل ده على thread لكل core. الحكاية دي اسمها parallelization: تحويل برنامج single-threaded لبرنامج بيستغل كل الـ CPUs المتاحة، وده أسهل طريقة تسرّع بيها البرنامج على الهاردوير الحديث.

2 — تفادي الانتظار على I/O

لو thread واحد واقف مستني I/O (disk، network، حتى page fault)، مفيش داعي كل البرنامج يقف. الـ scheduler يقدر يشغّل thread تاني عنده شغل مفيد يعمله بدل ما الـ CPU يقعد فاضي. عشان كده السيرفرات (web servers، databases) بتعتمد على threads بشكل تقيل — بتخلي الانتظار على I/O يتداخل (overlap) مع شغل مفيد تاني.

ملحوظة مهمة: تقدر تعمل نفس الحاجتين دول بـ processes منفصلة بدل threads. بس الـ threads بتشارك address space واحد، يعني مشاركة الـ data بينهم سهلة جداً (متغير global، pointer، إلخ) من غير أي تعقيد. الـ processes أنسب لما الشغل يكون منطقياً منفصل تماماً وميحتاجش يشارك structures في الـ memory.

* 3. تجربة: إنشاء Threads فعلياً

خلينا نشوف مثال بسيط: برنامج بينشئ thread-ين، كل واحد بيطبع حرف مختلف. 

#include <pthread.h>
#include <stdio.h>

void *say_hello(void *arg) {
    printf("%s\n", (char *) arg);
    return NULL;
}

int main(void) {
    pthread_t t1, t2;

    printf("main: begin\n");
    pthread_create(&t1, NULL, say_hello, "worker-1: A");
    pthread_create(&t2, NULL, say_hello, "worker-2: B");

    // join = استنى الـ thread ده لحد ما يخلص
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("main: end\n");
    return 0;
}

pthread_create بتقول للـ OS: "ابدأ تنفيذ الدالة دي في thread جديد، وده الـ argument اللي هتاخده". من لحظة الإنشاء، ممكن الـ thread الجديد يشتغل فوراً، أو يفضل واقف في حالة "ready" لحد ما الـ scheduler يديله فرصة. pthread_join بتوقّف الـ thread اللي نادى عليها (هنا main) لحد ما الـ thread المطلوب يخلص شغله.

الفكرة إن إنشاء thread شبه استدعاء دالة (function call)، بس بدل ما تنفّذها وترجع، الـ OS بيفتح لك مسار تنفيذ جديد ومستقل تماماً — ممكن يشتغل قبل ما pthread_create ترجع، وممكن بعدها بكتير. اللي بيحصل بعد كده بالظبط في إيد الـ scheduler، مش في إيدك.

Non-determinism من أول سطر

حتى المثال البسيط ده عنده أكتر من ترتيب تنفيذ ممكن. مثلاً، ممكن main تنشئ T1 وT2 الاتنين الأول وبعدين تستناهم، أو ممكن T1 يشتغل ويطبع "A" فوراً وهو لسه بيتعمله create قبل ما T2 حتى تتولد. وممكن كمان B تظهر قبل A لو الـ scheduler اختار يشغّل T2 الأول رغم إنه اتنشأ بعد T1 — مفيش أي ضمان إن اللي اتنشأ الأول هيشتغل الأول.

mainThread 1Thread 2
prints "main: begin"——
creates T1, T2——
waits (join T1)runs → prints "A"—
waits (join T2)doneruns → prints "B"
prints "main: end"—done

دي ترتيبة واحدة بس من عدة ترتيبات صحيحة كلها ممكنة لنفس الكود بالظبط. وده أول درس مهم: مع الـ concurrency، "إيه اللي هيحصل امتى" بقى سؤال مالوش إجابة واحدة ثابتة.

* 4. المشكلة الحقيقية: مشاركة Data بين Threads

المثال اللي فات كان كل thread شغال لوحده من غير ما يلمس حاجة مشتركة. لو دلوقتي جبنا thread-ين الاتنين بيعدّلوا نفس المتغير الـ global، إيه اللي هيحصل؟ 

static volatile long counter = 0;

void *bump(void *arg) {
    for (long i = 0; i < 10000000; i++)
        counter = counter + 1;
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, bump, NULL);
    pthread_create(&t2, NULL, bump, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %ld\n", counter); // المفروض 20000000
    return 0;
}

كل thread بيزوّد counter بـ 1، عشر مليون مرة، فالنتيجة المتوقعة 20,000,000. لو شغّلته، هتلاقي أحياناً بيطلعلك الرقم صح، وأحياناً تانية بيطلعلك رقم غلط — ومش نفس الرقم الغلط كل مرة! نفس الكود بالظبط، نفس الـ input، ونتايج مختلفة كل تشغيلة. السؤال: ليه؟

* 5. جوهر المشكلة: الـ Scheduling الغير متحكم فيه

السبب إن السطر البسيط counter = counter + 1 مش instruction واحدة على مستوى الـ CPU. الـ compiler بيحوّله لتلاتة instructions منفصلة (x86 تقريباً): 

mov  counter, %eax    // حمّل قيمة counter في register
add  $1, %eax          // زوّد الـ register بواحد
mov  %eax, counter     // رجّع القيمة من الـ register لـ counter

ولو الـ interrupt (زي timer interrupt بتاع الـ scheduler) حصل في نص الطريق ده، هتحصل كارثة. خلينا نتخيل counter = 50 ونتابع T1 وT2 خطوة بخطوة:

الوقتThread 1Thread 2counter في الـ RAM
t0قبل ما يبدأ—50
t1mov → eax=50—50
t2add → eax=51—50
t3⚡ timer interrupt — context switch لـ T250
t4(مجمد، eax=51 محفوظة في TCB)mov → eax=5050
t5—add → eax=5150
t6—mov → يخزّن 5151
t7⚡ context switch يرجع لـ T151
t8يكمل: mov → يخزّن eax المحفوظة (51)—51

النتيجة النهائية: counter = 51، رغم إن فيه زيادتين اتنفذوا فعلاً! T2 خزّن 51 ثم T1 رجع خزّن نفس القيمة القديمة اللي كانت في register بتاعه (51 برضو) فوق القيمة اللي T2 حطها — يعني زيادة T2 "ضاعت" فعلياً. ده اسمه lost update. بما إن التوقيت بتاع الـ interrupt عشوائي، كل تشغيلة ممكن تضيع فيها عدد مختلف من الزيادات، وعشان كده كل مرة بتطلع نتيجة مختلفة.

المصطلحات الأساسية
Critical Section
أي جزء من الكود بيلمس shared resource (متغير، data structure) ولازم ميتنفذش من أكتر من thread في نفس الوقت.
Race Condition (Data Race)
لما أكتر من thread يدخلوا الـ critical section في نفس الفترة تقريباً، والنتيجة تبقى محتاجة لتوقيت معين عشان تطلع صح.
Indeterminate Program
برنامج فيه race condition واحدة أو أكتر، فالـ output بتاعه بيتغير من تشغيلة للتانية — عكس الحتمية (determinism) اللي متعودين عليها من الكمبيوتر.
Mutual Exclusion
الخاصية اللي بنتمناها: لو thread داخل الـ critical section، الباقي يتمنعوا من الدخول لحد ما يخرج.

(المصطلحات دي أصلها من إدسخر دايكسترا Edsger Dijkstra، اللي حط أساسات الموضوع ده من الستينات وأخد Turing Award على شغله في المجال.)

* 6. اللي إحنا محتاجينه: Atomicity

الحل النظري السهل: لو الهاردوير كان بيدّينا instruction واحدة سحرية زي memory-add address, value بتضمن إنها تتنفذ atomically — يعني كوحدة واحدة، إما تتنفذ بالكامل أو محصلش حاجة خالص، من غير أي حالة نص-نص ممكن الـ interrupt يمسكها — المشكلة كانت هتتحل من نفسها. بس ده مش عملي: مينفعش نطلب من الهاردوير instruction مخصصة لكل عملية معقدة (زي تحديث B-tree كامل مثلاً).

فبدل كده، الهاردوير بيدّينا مجموعة صغيرة من الـ atomic instructions العامة (هنشوفها بالتفصيل في الفصول الجاية)، والـ OS مع المبرمج بيبنوا فوقها حاجة اسمها synchronization primitives — زي الـ locks — عشان نقدر نلف أي critical section عايزينها ونضمن إن thread واحد بس يدخلها في كل مرة.

* 7. مشكلة تانية غير الـ Race: الانتظار

مش كل تفاعل بين threads بيكون سباق على data مشتركة. أحياناً thread محتاج ببساطة يستنى thread تاني يخلص حاجة معينة قبل ما يكمل — زي process بيعمل disk I/O وبيتحط "نايم" لحد ما الـ I/O يخلص، وبعدين لازم حد "يصحّيه". الآلية دي (sleep / wake up) هتتغطى في فصل تاني عن الـ condition variables.

* 8. طب ليه ندرس الموضوع ده في مادة OS؟

الإجابة باختصار: تاريخياً، الـ OS نفسه كان أول برنامج concurrent في الدنيا. الـ kernel بيتقاطع مع نفسه طول الوقت بسبب الـ interrupts اللي بتحصل في أي لحظة، وبرضو لازم يحدّث structures داخلية مشتركة (page tables، process lists، bitmaps بتاعة تخصيص المساحة، inodes بتاعة الملفات) بأمان.

مثال بسيط: process-ين بيحاولوا يعملوا append لنفس الملف في نفس الوقت — كل واحد لازم يحجز block جديد، يسجّله في inode الملف، ويحدّث حجم الملف. لو مفيش synchronization صح على الخطوات دي، هتحصل نفس مشكلة الـ lost update اللي شفناها فوق، بس جوه الـ kernel نفسه. عشان كده أي structure جوه الـ kernel لازم توصله بحذر شديد وبأدوات synchronization صحيحة.

* 9. خلاصة واللي جاي

الفصل ده وضع المشكلة، مش الحل. اللي اتعلمناه:

  • الـ thread = نقطة تنفيذ إضافية جوه process واحدة، بتشارك address space لكن ليها stack وregisters خاصة.
  • بنستخدم threads عشان الـ parallelism وعشان نتفادى وقوف البرنامج على I/O بطيئة.
  • ترتيب تنفيذ الـ threads مش متوقع أبداً — الـ scheduler هو اللي بيقرر.
  • مشاركة data من غير حماية بتنتج race conditions وnتايج indeterminate (زي مثال الـ counter).
  • الحل جاي من فكرة الـ atomicity: الهاردوير + الـ OS بيقدموا synchronization primitives (locks، وبعدين condition variables) نبني بيها critical sections آمنة.

الفصول الجاية في الكتاب هتبني على الأساس ده: إزاي نعمل locks فعلياً (باستخدام test-and-set/compare-and-swap وغيرها)، وإزاي نستخدم condition variables للـ sleep/wake coordination. فيه كمان homework تفاعلي في الكتاب اسمه x86.py بيسيبك تجرّب بنفسك ترتيبات مختلفة للـ interrupts وتشوف تأثيرها على برامج زي دي — يستاهل تجربة لو حابب تلعب بالمفهوم بإيدك.
